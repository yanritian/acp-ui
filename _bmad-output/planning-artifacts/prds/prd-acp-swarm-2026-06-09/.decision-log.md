# Decision Log — acp-swarm PRD v2.0.0

> 记录 PRD 编写过程中的所有决策、变更和覆盖。

---

## v1 → v2 变更（基于 3 份 Reviewer 审查 + 8 份文档交叉分析）

### DEC-001: 产品定位为独立产品

- **上下文**: acp-swarm 最初是 acp-ui 的 swarm_orchestrator.rs 子模块
- **决策**: 将 acp-swarm 定位为独立产品，有自己的 PRD、仓库、版本管理
- **依据**: 新仓库建设计划明确要求仓库拆分

### DEC-002: v1 聚焦编程领域

- **决策**: v1 MVP 只聚焦编程领域
- **依据**: 最容易 demo，社区最熟悉

### DEC-003: v1 只提供 Rust 和 TypeScript SDK

- **决策**: Python SDK 留给 v2+
- **依据**: 减少 v1 工作量

### DEC-004: v1 只支持 Star 和 Chain 拓扑

- **决策**: Mesh/Pipeline/Hierarchical 留给 v2+
- **依据**: 两种足够 demo

### DEC-005: v1 只支持 Auto 和 Queen Evaluator

- **决策**: Adversarial/Hybrid 留给 v2+
- **依据**: Auto + Queen 足够 v1

### DEC-006: 开源许可证 = MIT

- **决策**: MIT 许可证
- **依据**: 更宽松，有利于社区采纳

---

### DEC-007: [v2] 补充能力体系 5 个 Phase

- **上下文**: v1 PRD 只覆盖 RFC-001 和总纲的核心协议层，完全缺失能力体系文档的 Skill 路由、Checkpoint、Hook 扩展、ACP 消息总线、Tool 沙箱、测试矩阵
- **决策**: 在 v2 PRD 中新增 FR-29 到 FR-37，覆盖全部 5 个 Phase
- **依据**: 交叉分析发现这些是将 acp-swarm 从"纯协议"变成"完整平台"的关键能力层

### DEC-008: [v2] 补充 crates/ Workspace 架构

- **上下文**: v1 PRD 没有提到 crates/ 拆分
- **决策**: 新增 FR-38，定义 9 个 crate 的拆分方案
- **依据**: 新仓库建设计划明确要求 Cargo workspace

### DEC-009: [v2] 补充开源策略

- **上下文**: 开源策略审查发现 PRD 缺 README 策略、文档体系、贡献者体验
- **决策**: 新增 FR-39 到 FR-42
- **依据**: 开源项目成功不仅靠代码，还靠文档和社区

### DEC-010: [v2] Queen 选举不再强制 claude_code

- **上下文**: 对抗审查指出"异构蜂群"和"Queen 必须 claude_code"矛盾
- **决策**: 任何 Worker 可参选，claude_code 有 +0.1 加分
- **依据**: 消除"异构"承诺与实际限制之间的矛盾

### DEC-011: [v2] Queen Lease TTL 从 30s 上调到 120s

- **上下文**: 对抗审查指出 30s TTL 在推理时可能过期
- **决策**: TTL 120s + Busy Queen 延期模式
- **依据**: 防止 Goal 分解过程中 Queen 租约过期

### DEC-012: [v2] Reconcile Loop 新增震荡检测

- **上下文**: 对抗审查指出 Reconcile Loop 可能无限循环
- **决策**: 相同反馈连续出现 3 次 → Queen 介入
- **依据**: 防止 Agent 在同一个错误上无限迭代

### DEC-013: [v2] 反馈格式从纯文本改为结构化

- **上下文**: Rubric 审查指出 FR-4 反馈格式未定义
- **决策**: 反馈格式为 EvaluationResult { converged, feedback, stdout, stderr, duration_ms }
- **依据**: 结构化反馈便于 UI 展示和调试

### DEC-014: [v2] EventStore 抽象层

- **上下文**: 对抗审查指出 SQLite 是 v2 迁移陷阱
- **决策**: 新增 EventStore trait，v1 SQLite 实现，v2 PostgreSQL
- **依据**: 无缝切换，不需要业务逻辑改动

### DEC-015: [v2] Token 预算交叉验证

- **上下文**: 对抗审查指出 Worker 自报 Token 不可信
- **决策**: CLI Worker 由编排引擎解析输出，HTTP Worker 由 SDK 报告 + 交叉验证
- **依据**: 防止恶意 Worker 消耗无限 Token

### DEC-016: [v2] SM-1 从 GitHub Stars 改为周活跃蜂群

- **上下文**: 开源策略审查指出 Stars 是虚荣指标
- **决策**: SM-1 = 周活跃蜂群数 100，Stars 降级为 SM-8（辅助）
- **依据**: 衡量真实使用，不是鼓掌

### DEC-017: [v2] 新增 UJ-4（Worker 调试旅程）

- **上下文**: 对抗审查指出 PRD 全是 happy path，缺调试旅程
- **决策**: 新增 UJ-4：Alex 调试失败 Worker
- **依据**: Worker 开发者大部分时间在调试，不是庆祝

### DEC-018: [v2] 新增 30 天留存指标

- **上下文**: 开源策略审查指出缺留存指标
- **决策**: 新增 SM-4 = 30 天留存 ≥ 30%
- **依据**: 用户是否真正回来使用

### DEC-019: [v2] NFR-3 量化

- **上下文**: Rubric 审查指出"不卡顿"不可测量
- **决策**: NFR-3 = WebSocket 推送后 500ms 内渲染
- **依据**: 可测量的性能目标

### DEC-020: [v2] 新增 SM-3 分层

- **上下文**: 对抗审查指出 80% 收敛率可通过 trivial Goal 刷
- **决策**: SM-3 分 3 层：整体 80%, 3+ 迭代 50%, 5+ 迭代 30%
- **依据**: 区分简单 Goal 和复杂 Goal 的收敛率

## 数据模型冲突决策

### DEC-021: Worker 能力声明采用 WorkerCapabilityManifest

- **上下文**: 战略聚焦用 `WorkerCapabilities { strengths, weaknesses }`，能力体系/RFC-001/总纲用 `WorkerCapabilityManifest { skills: Vec<WorkerSkill> }`
- **决策**: 以 RFC-001/能力体系/总纲为准，使用 `WorkerCapabilityManifest`
- **依据**: 3 份文档已收敛到更精细的 WorkerSkill 模型，战略聚焦是初版
