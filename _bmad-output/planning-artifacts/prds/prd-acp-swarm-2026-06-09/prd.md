## 1. Vision

**acp-swarm 是异构 Agent 蜂群编排引擎。**

它不执行任何具体任务——不写代码、不写小说、不训练模型、不生成图片。它只做一件事：**让多个 Agent 按照目标（Goal）协作，自动迭代直到目标达成。**

类比：
- **浏览器**渲染 HTML/CSS/JS，但不生产网页内容。
- **Kubernetes** 编排容器，但不构建应用。
- **acp-swarm** 编排 Agent，但不执行具体任务。

**核心创新**：Goal-Driven 模型。传统编排器给 Worker 分配"任务"（固定步骤），acp-swarm 给 Worker 设定"目标"（完成条件）。Worker 进入 **Reconcile Loop**——执行、评估、反馈、再执行——直到完成条件满足（Converged）或预算耗尽。这与 Codex `/goal` 和 Claude Code `/goal` 的理念一致，但 acp-swarm 让它跨 Agent 工作。

**开源差异化**：Codex Ultracode 和 Claude Dynamic Workflows 是闭源蜂群——只能用自家 Agent。acp-swarm 是开源异构蜂群——任何 Agent（Codex、Claude Code、Gemini、自研 Agent）都能通过 ACP 协议加入。与 Ruflo（Claude-only）相比，acp-swarm 是真正异构的。

**一句话**：acp-swarm 不做 Agent，它让 Agent 像团队一样协作。

## 2. Target User

### 2.1 Primary Persona

**Alex，Agent 开发者，全栈工程师。**

Alex 已经用 Codex 或 Claude Code 做日常开发，或者自己用 LangChain/AutoGen 搭了个 Agent。他遇到了瓶颈：

- 单个 Agent 搞不定复杂任务（需要代码生成 + 代码审查 + 测试，一个 Agent 做不好所有事）
- 想让多个 Agent 协作，但自己写调度逻辑太麻烦（状态管理、失败重试、结果合并）
- 试过 Codex 的 subagent 或 Claude 的 Dynamic Workflows，但被锁定在单一生态里

Alex 需要一个**开源的、协议驱动的、能接入任意 Agent 的编排引擎**。他不想要另一个 Agent 框架，他想要一个**让现有 Agent 协作的基础设施**。

### 2.2 Jobs To Be Done

- **功能需求**：让多个异构 Agent（Codex + Claude Code + 自研 Agent）协作完成复杂编程任务
- **情感需求**：感觉自己掌握了控制权（不是被 Agent 牵着走，而是编排 Agent）
- **社交需求**：在开源社区展示"我搭了个多 Agent 蜂群"的技术能力
- **上下文需求**：能在本地跑 demo，能在 CI/CD 里集成，能在生产环境部署

### 2.3 Non-Users (v1)

- **非技术用户**：v1 不提供 no-code 界面，需要会写代码（Rust/TypeScript/Python 任一）
- **Agent 框架开发者**：acp-swarm 不替代 LangChain/AutoGen，而是与它们协作
- **只想用单一 Agent 的人**：如果 Codex 单 Agent 能搞定，不需要 acp-swarm
- **追求生产就绪的企业用户**：v1 是 MVP，不适合直接上生产（v2+ 考虑企业特性）

### 2.4 Key User Journeys

**UJ-1. Alex 第一次跑通多 Agent 协作 demo。**

- **Persona + context**: Alex 刚 clone 了 acp-swarm，想在 5 分钟内看到"多个 Agent 协作"的效果。
- **Entry state**: 本地有 Codex CLI 或 Claude Code CLI 已配置（有 API key）。只需一个即可（One-Agent Demo Mode）。
- **Path**:
  1. `cargo run --example quickstart` 启动编排引擎
  2. 终端显示：`acp-swarm listening on http://localhost:9090`
  3. `acp-swarm worker register --type codex --id codex-1`
  4. `acp-swarm run --goal examples/goals/fix-ts-errors.goal`
  5. 终端实时输出：`[Goal fix-ts-errors] iteration 0 → evaluating → not converged (5 errors remaining) → iteration 1 → converged ✓`
  6. 3 分钟后，终端显示：`Goal converged after 2 iterations, 45000 tokens used`
- **Climax**: Alex 看到终端上 Goal 状态从 "Iterating" 变成 "Converged"，Token 消耗显示 45000/100000。
- **Resolution**: Alex 截图发推特："刚用 acp-swarm 让 Codex 自动修了 50 个 TS 错误，2 轮迭代就收敛了，爽！"
- **Edge case**: 如果只有一个 Worker（比如只有 Codex），使用 Chain 拓扑（单 Worker 串行），也能跑通。

**UJ-2. Alex 接入自己的 Agent。**

- **Persona + context**: Alex 有个用 LangChain 搭的"代码审查 Agent"，想让它加入蜂群。
- **Entry state**: 已有 Python Agent，实现了 HTTP 接口。
- **Path**:
  1. 阅读 `docs/worker-sdk-python.md`
  2. `pip install acp-worker-sdk`
  3. 在 Python Agent 里加 5 行代码（略）
  4. 启动 Python Agent
  5. Dashboard 自动发现新 Worker，显示 "my-reviewer (custom)"
  6. 在 .goal 文件里声明这个 Worker 擅长 "code-review"
  7. 下次执行 Goal 时，Skill 路由自动把审查任务路由给 my-reviewer
- **Climax**: Alex 看到自己的 Agent 被编排器调度，和其他 Worker 协作完成 Goal。
- **Resolution**: Alex 给 acp-swarm 提了个 PR，分享 Python SDK 的使用示例。

**UJ-3. Alex 在 CI/CD 里集成 acp-swarm。**

- **Persona + context**: Alex 想在 GitHub Actions 里用 acp-swarm 自动修 bug。
- **Entry state**: 有 GitHub repo，issue 里有 bug 报告。
- **Path**:
  1. 在 `.github/workflows/fix-bugs.yml` 里配置 acp-swarm CLI
  2. 当 issue 打上 "bug" 标签时，自动触发 workflow
  3. `acp-swarm run --goal "Fix issue #42" --workers codex,claude-code --topology star`
  4. acp-swarm 在 CI 环境启动 Worker，执行 Goal，生成 PR
  5. PR 描述里包含："Generated by acp-swarm, converged after 3 iterations, 67000 tokens used"
- **Climax**: Alex 收到 GitHub 通知：新 PR 已创建，CI 测试通过。
- **Resolution**: Alex merge PR，issue 自动关闭。
- **Edge case**: 如果 Goal 在 CI 中 `BudgetExhausted`，PR 描述标记 "Budget exhausted, manual intervention required"，不自动 merge。

**UJ-4. Alex 调试一个失败的 Worker。**

- **Persona + context**: Alex 注册了一个自定义 Worker，但 Goal 一直不收敛。
- **Entry state**: Worker 已注册，但状态显示 "error"。
- **Path**:
  1. `acp-swarm watch --worker my-reviewer` 查看实时事件流
  2. 发现事件：`goal.iterating → evaluation.feedback: "Command not found: npm"`
  3. Alex 意识到 Worker 环境没安装 npm
  4. 修复 Worker 环境，重新注册
  5. `acp-swarm goal retry goal-001` 重试
  6. Goal 收敛 ✓
- **Climax**: Alex 通过事件流定位到问题根因（不是代码 bug，是环境问题）。
- **Resolution**: Alex 在 Worker 文档里加了一条："需要预装 npm"。

## 3. Glossary

*下游工作流（架构、UX、Epic）和读者必须严格使用以下术语。PRD 中不允许引入同义词。*

- **Goal（目标）** — 蜂群编排的核心抽象。包含描述（description）、完成条件（CompletionCondition）、评估器（Evaluator）、Token 预算（token_budget）、最大迭代轮数（max_iterations）。Goal 不是一次性任务，而是进入 Reconcile Loop 直到收敛。定义于 `crates/swarm-engine/src/goal.rs`。

- **Worker（工作者）** — 加入蜂群的 Agent 实例。实现 Worker Protocol（register、heartbeat、goal/receive、goal/progress、goal/result）。声明自己的能力（`WorkerCapabilityManifest` 包含 `skills: Vec<WorkerSkill>`、`max_concurrency`、`max_context_tokens`）。

- **WorkerSkill** — Worker 声明的技能。包含 `name`、`proficiency`（0.0-1.0 熟练度）、`execution_count`、`success_rate`、`avg_duration_ms`、`required_permissions`。定义于 `crates/acp-core/src/skill.rs`。

- **Queen（蜂后）** — 特殊角色的 Worker。负责 Goal 分解（Decomposition）、结果评估（Evaluation）、冲突仲裁。通过 Queen Lease 选举机制产生，防止脑裂。Queen 也是 Worker，但有额外权限。v1 中任何 Worker 可参选，`claude_code` 类型有加分但不强制。

- **Reconcile Loop（收敛循环）** — Goal-Driven 模型的核心机制。Worker 执行 Goal → Evaluator 验证 CompletionCondition → 不通过则带反馈重新执行 → 直到 Converged 或 BudgetExhausted。包含**震荡检测**：相同反馈连续出现 3 次则 Queen 介入。定义于 `crates/swarm-engine/src/reconcile.rs`。

- **CompletionCondition（完成条件）** — 客观可验证的条件，定义什么算"做完了"。8 种类型：CommandSuccess、OutputContains、OutputMatches、All、Any、FileCheck、HttpHealthCheck、QueenJudgment。

- **Evaluator（评估器）** — 验证 CompletionCondition 的角色。4 种类型：Auto、Queen、Adversarial、Hybrid。v1 实现 Auto + Queen，v2+ 实现 Adversarial + Hybrid。

- **Iteration（迭代轮次）** — Reconcile Loop 的一轮。从 0 开始。每轮迭代追加结构化反馈到 Goal 描述末尾。反馈格式为 `EvaluationResult { converged, feedback, stdout, stderr, duration_ms }`。

- **Token Budget（Token 预算）** — Goal 的 Token 消耗上限，跨迭代轮次累计。防止 Agent 在一个 Goal 上消耗无限 Token。

- **.goal File（Goal 定义文件）** — YAML 格式，定义 Goal 图（多个 Goal 的依赖关系、Worker 分配、CompletionCondition）。类比 Kubernetes 的 Deployment YAML。

- **GoalGraph（目标依赖图）** — 管理多个 Goal 之间的依赖关系（DAG）。`ready_goals()` 返回所有无依赖或依赖已 Converged 的 Goal。Star 和 Chain 是 GoalGraph 的两种特例。

- **Topology（拓扑）** — Worker 之间的协作模式。v1 支持 Star（Queen 分解 + Workers 并行）和 Chain（Goal 依赖链顺序执行）。v2+ 支持 Mesh、Pipeline、Hierarchical。

- **ACP（Agent Communication Protocol）** — Agent 与编排器之间的通信协议。包含 Worker Protocol、Goal Protocol、Event Protocol、Embed Protocol。

- **AcpMessage** — ACP 协议的统一消息格式。`{ type, version, id, timestamp, source_id, target_id, payload, correlation_id }`。所有传输层（Tauri/stdio/WebSocket/HTTP）都使用相同的消息格式。

- **AcpMessageBus** — ACP 消息总线。所有消息通过此总线路由。支持定向路由（target_id）和全局广播。定义于 `crates/event-bus/src/lib.rs`。

- **SDK** — Worker 开发者工具包。v1 提供 Rust SDK 和 TypeScript SDK。v2+ 提供 Python SDK。

- **SwarmSkillRouter** — Skill 路由器。根据 `proficiency * 0.4 + success_rate * 0.4 + (1/load) * 0.2` 评分，将 Skill 路由到最佳 Worker。定义于 `crates/acp-core/src/skill.rs`。

- **Checkpoint（检查点）** — Workflow Stage 成功后的状态快照。包含文件变更（`FileChange`）、输入/输出数据。支持回溯（Rollback）到任意检查点。定义于 `crates/workflow-engine/src/checkpoint.rs`。

- **Dashboard（控制面板）** — Web UI，显示 Worker 状态、Goal 进度、Token 消耗、Event Log。通过 WebSocket 消费 Event Protocol 事件流。

- **EventStore** — 事件存储抽象层。v1 使用 SQLite 实现，v2+ 可扩展到 PostgreSQL。定义于 `crates/acp-core/src/db/events.rs`。

- **ToolSandbox（工具沙箱）** — Worker 工具执行的安全隔离环境。包含路径白名单、拒绝模式（`.env`, `.ssh`）、网络隔离、超时控制。定义于 `crates/tool-sandbox/src/lib.rs`。

- **HookType** — Hook 类型枚举。v1 在原有 4 种（PreToolUse/PostToolUse/PostToolUseFailure/Stop）基础上新增 12 种蜂群级别 Hook（PreTask/PostTask/OnWorkerError/OnSwarmStart 等）。

## 4. Features

### 4.1 Goal-Driven 编排引擎（核心）

**描述**：acp-swarm 的核心创新。传统编排器分配"任务"（一次性执行），acp-swarm 分配"目标"（Reconcile Loop 迭代到收敛）。Realizes UJ-1, UJ-2, UJ-3。

#### FR-1: Goal 结构体定义

系统必须定义 `Goal` 数据结构，包含以下字段：
- `id: String` — 唯一标识
- `description: String` — 人类可读的目标描述（每轮迭代追加反馈）
- `parent_task_id: String` — 所属蜂群任务 ID
- `parent_goal_id: Option<String>` — 父 Goal ID（用于嵌套 Goal）
- `completion_condition: CompletionCondition` — 完成条件
- `evaluator: Evaluator` — 评估器
- `executor: String` — 执行者 Worker ID
- `depends_on: Vec<String>` — 依赖的 Goal ID 列表
- `token_budget: u64` — Token 预算上限
- `tokens_used: u64` — 已消耗 Token 数
- `max_iterations: u32` — 最大迭代轮数
- `current_iteration: u32` — 当前迭代轮数
- `per_iteration_timeout_ms: u64` — 单轮超时（默认 300000ms）
- `status: GoalStatus` — 当前状态
- `iteration_log: Vec<IterationRecord>` — 每轮迭代的评估记录
- `created_at: DateTime<Utc>` / `converged_at: Option<DateTime<Utc>>`
- `output_files: Vec<String>` — Worker 产出的文件路径（用于 Checkpoint）
- `metadata: serde_json::Value` — 自由格式元数据

**Consequences:**
- 定义于 `crates/swarm-engine/src/goal.rs`
- 所有字段必须有 serde 序列化支持
- `is_terminal()` 返回 true 当 status 为 Converged/BudgetExhausted/MaxIterReached/Failed/Cancelled
- `remaining_budget()` 返回 `token_budget.saturating_sub(tokens_used)`

#### FR-2: CompletionCondition 枚举

系统必须定义 8 种完成条件类型：
- `CommandSuccess { command, args, cwd, env }` — 命令退出码为 0
- `OutputContains { command, args, pattern, case_sensitive }` — 输出包含指定文本
- `OutputMatches { command, args, regex }` — 输出匹配正则
- `All { conditions: Vec<CompletionCondition> }` — 所有子条件满足（AND）
- `Any { conditions: Vec<CompletionCondition> }` — 任一子条件满足（OR）
- `FileCheck { path, content_contains, content_matches, max_size_bytes }` — 文件存在且内容匹配
- `HttpHealthCheck { url, method, expected_status, body_contains }` — HTTP 返回 2xx
- `QueenJudgment { criteria }` — Queen 主观判断

**Consequences:**
- 每种条件类型必须可程序化执行
- 条件可组合（All/Any 形成条件树）
- 执行结果必须是确定性的
- `ConditionEvaluator::evaluate()` 方法接收 `CompletionCondition` + `workspace_root`，返回 `EvaluationResult`

#### FR-3: GoalStatus 状态机

系统必须定义 Goal 的状态机：
- `Pending` → `Active` → `Evaluating` → `Converged` / `Iterating` → `Active` → ...
- `Active` → `Failed(String)` / `Cancelled`
- `Evaluating` → `BudgetExhausted` / `MaxIterReached`

**Consequences:**
- 状态转移必须合法
- `is_terminal()` 返回 true 当终态
- 每次状态转移必须 emit 事件（`goal.status_changed`）

#### FR-4: Reconcile Loop 实现

系统必须实现 Reconcile Loop（8 步算法）：

```
LOOP:
  Step 1: Token Budget Check
    IF tokens_used >= token_budget → BudgetExhausted, RETURN

  Step 2: Max Iteration Check
    IF current_iteration >= max_iterations → MaxIterReached, RETURN

  Step 3: Build worker message
    worker_message = build_worker_message(goal)  // 包含 iteration、remaining_budget、completion_condition

  Step 4: Dispatch to Worker
    goal.status = Active; emit
    execution_result = execute_on_worker(goal.executor, worker_message, timeout)
    IF Err → Failed, RETURN
    tokens_used += execution.tokens_used

  Step 5: Evaluate completion condition
    goal.status = Evaluating; emit
    evaluation = evaluate_goal(goal, execution)  // 4 种 Evaluator 分支

  Step 6: Record iteration
    record = IterationRecord { iteration, started_at, finished_at, worker_output, tokens_used, cumulative_tokens, evaluation, duration_ms, tool_calls, files_modified }
    iteration_log.push(record)

  Step 7: Check convergence
    IF evaluation.converged → Converged, RETURN

  Step 8: Oscillation detection + Prepare next iteration
    IF same feedback appears 3 consecutive iterations → Queen intervenes (change Worker or modify Goal)
    current_iteration += 1
    goal.status = Iterating; emit
    goal.append_feedback(iteration, evaluation.feedback)
    // Continue loop → back to Step 1
```

**Consequences:**
- 反馈格式为结构化 `EvaluationResult`（不是纯文本）
- **震荡检测**：相同 `evaluation.feedback` 连续出现 3 次，Queen 介入判断是否更换 Worker 或修改 Goal 描述
- Token 消耗跨迭代累计
- Dashboard 显示当前迭代轮次和 Token 消耗进度条

#### FR-5: Evaluator 分离

系统必须实现 Executor/Evaluator 分离：
- `Auto` — 直接跑 CompletionCondition 中的命令
- `Queen` — 先跑 Auto，通过后让 Queen Worker 做主观审查
- `Adversarial { evaluator_worker: String }` — 让另一个 Worker 审查（不能等于 executor）
- `Hybrid { auto_condition: CompletionCondition, human_evaluator: Box<Evaluator> }` — 先跑客观检查，通过后交主观评估

**Consequences:**
- Worker 不能自己说自己"完成了"
- Adversarial 评估器不能等于 executor（防止自我审查）
- Queen 评估必须记录评估理由（`metadata.evaluation_reasoning`）

**Notes:**
- [ASSUMPTION] v1 实现 Auto + Queen，Adversarial + Hybrid 留给 v2+
- Queen 评估的 Token 消耗计入 Goal 的 `token_budget`（统一计费）

### 4.2 Worker Protocol（Worker 接入协议）

**描述**：任何 Agent 只要实现以下 5 个接口，就能成为 acp-swarm 的 Worker。Realizes UJ-1, UJ-2。

#### FR-6: Worker 注册接口

`POST /acp/worker/register`
- Request: `{ worker_id, worker_type, version, capabilities: WorkerCapabilityManifest }`
- Response: `{ status: "registered", worker_id, heartbeat_interval_ms }`

**Consequences:**
- `WorkerCapabilityManifest` 包含 `skills: Vec<WorkerSkill>`（不是旧的 `strengths/weaknesses`）
- 注册信息通过 `EventStore` 持久化（SQLite → PostgreSQL 可替换）
- 注册成功 emit `worker.registered` 事件

#### FR-7: Worker 心跳接口

`POST /acp/worker/heartbeat`
- Request: `{ worker_id, status, current_load, active_goals, memory_usage_mb, uptime_seconds }`
- Response: `{ status: "ok" }`

**Consequences:**
- 默认 `heartbeat_interval_ms = 10000`
- 连续 3 次未收到心跳 → Worker 失联 → emit `worker.disconnected` → 触发故障转移

#### FR-8: Worker 接收 Goal 接口

`POST /acp/worker/goal/receive`
- Request: `{ goal_id, description, iteration, feedback_from_last_iteration, workspace_path, git_branch, token_budget, timeout_ms }`
- Response: `{ status: "accepted", execution_id, estimated_duration_ms }`

**Consequences:**
- Worker 只能在 `git_branch`（格式：`worker/{worker_id}/goal/{goal_id}`）上工作
- `feedback_from_last_iteration: Option<EvaluationResult>` — 第一轮为 null

#### FR-9: Worker 进度汇报接口（可选）

`POST /acp/worker/goal/progress`
- Request: `{ execution_id, goal_id, progress_pct, current_action, tokens_used, files_modified }`
- Response: `{ status: "ok" }`

**Consequences:**
- 可选接口，不实现不影响 Goal 执行
- 实现后 Dashboard 显示实时进度条

#### FR-10: Worker 返回结果接口

`POST /acp/worker/goal/result`
- Request: `{ execution_id, goal_id, success, output, tokens_used, files_modified, tool_calls, git_commit_hash }`
- Response: `{ status: "received", next_action: "evaluating" }`

**Consequences:**
- 编排器收到结果后自动进入评估阶段
- `git_commit_hash` 用于 Checkpoint 回溯

### 4.3 .goal 文件格式（Goal 定义语言）

**描述**：YAML 格式的 Goal 定义文件。Realizes UJ-1, UJ-3。

#### FR-11: .goal 文件 Schema

系统必须支持完整 YAML Schema（详见总纲 §2.2）：
- 元数据：name, description, version, author, tags
- Workers 声明：id, type, fallback
- Goals 列表：id, executor, description, condition(8种), evaluator(4种), depends_on, budget, max_iter, timeout_ms, checkpoint
- 顶层 Goal：condition, evaluator

#### FR-12: .goal 文件解析器

`goal-parser` crate：
- 输入：`.goal` 文件路径
- 输出：`GoalGraph`（包含 `Vec<Goal>` + 依赖关系）
- 错误：`GoalParseError { line, column, message }`

**Consequences:**
- 验证 `executor` 必须是 `workers` 中声明的 Worker ID
- 验证 `depends_on` 不能形成循环依赖（拓扑排序检查）
- 为每个 Goal 分配唯一 `git_branch`

#### FR-13: .goal 文件示例库

`examples/goals/` 目录：
- `hello-swarm.goal` — 5 分钟快速开始（echo mock Worker）

- `generate-api-docs.goal` — 文档领域
- `refactor-module.goal` — 重构领域

**Consequences:**
- `hello-swarm.goal` 必须能用 echo mock Worker 跑通（不依赖真实 CLI）
- 每个示例包含 README 说明预期行为和 Token 消耗

### 4.5 拓扑执行引擎

**描述**：Star + Chain 拓扑。Realizes UJ-1, UJ-3。

#### FR-16: Star 拓扑

Queen Worker 分解顶层 Goal → Sub-Goals 分配给 Workers 并行 → 全部 Converged 后 Queen 验证顶层条件。

**Consequences:**
- Queen 不再强制 `claude_code` 类型。任何 Worker 可参选，`claude_code` 在选举中有加分。
- 如果没有 `claude_code` Worker，第一个注册的 Worker 自动成为 Queen（降级模式）

#### FR-17: Chain 拓扑

Goal 按依赖链顺序执行。每个 Goal 必须等前一个 Converged 才能开始。

### 4.6 Queen 选举与防脑裂

**描述**：ZooKeeper 租约模式。Realizes UJ-1。

#### FR-18: Queen Lease 租约

- `ttl_seconds: u64` — **默认 120 秒**（从 30s 上调，避免推理时过期）
- `renew_interval_seconds: u64` — 默认 30 秒
- **Busy Queen 模式**：Queen 正在执行 Goal 分解时，租约自动延期（防止中途过期触发重新选举）

#### FR-19: Queen 选举算法

1. 收集所有已注册 Worker（不再限制类型）
2. 计算得分：`proficiency * 0.4 + success_rate * 0.4 + (1/load) * 0.2`
3. `claude_code` 类型额外加分（`+0.1`），因为推理能力更强
4. 得分最高的成为 Queen
5. 分配租约

#### FR-20: 防脑裂验证器

- 验证命令是否来自有效 Queen
- 无效 Queen 的命令拒绝执行
- 记录所有拒绝命令

### 4.8 事件流与可观测性

**描述**：统一事件流。Realizes UJ-1, UJ-3, UJ-4。

#### FR-25: 事件类型定义（20+ 种）

系统必须定义以下事件类型（详见总纲 §2.3）：

**Worker 生命周期**：`worker.registered`, `worker.heartbeat`, `worker.disconnected`, `worker.reconnected`

**Goal 生命周期**：`goal.submitted`, `goal.active`, `goal.progress`, `goal.evaluating`, `evaluation.complete`, `goal.iterating`, `goal.converged`, `goal.failed`, `goal.blocked`

**Checkpoint**：`checkpoint.created`, `rollback.started`, `rollback.complete`

**蜂群级别**：`swarm.started`, `swarm.converged`, `swarm.failed`

**Queen**：`queen.elected`, `queen.failover`

**Consequences:**
- 统一格式：`AcpEvent { type, timestamp, task_id, data }`
- 通过 `AcpMessageBus` 广播
- 通过 `EventStore` 持久化（SQLite，可替换）
- 传输方式：WebSocket / SSE / Tauri Events / Polling

#### FR-26: 指标收集

Worker 数量、Goal 成功率、平均迭代轮次、平均 Token 消耗、平均执行时长。

### 4.9 Token 预算管控

**Consequences:**

#### FR-28: Token 预算验证

**新增（审查修复）**：Token 消耗不再完全依赖 Worker 自报告。

### 4.10 Skill 路由系统（NEW）

**描述**：Worker 声明能力，编排引擎根据 Skill 路由任务到最佳 Worker。Realizes UJ-2。

**来源**：能力体系 §2（`swarm_skill_registry.rs`）。

#### FR-29: Worker 能力注册

Worker 注册时必须提交 `WorkerCapabilityManifest`：
- `worker_id, worker_type`
- `skills: Vec<WorkerSkill>`（每个 Skill 包含 name, proficiency, success_rate, avg_duration_ms）
- `max_concurrency, max_context_tokens, output_formats`

#### FR-30: Skill 路由算法

`SwarmSkillRouter` 根据评分路由 Skill 到最佳 Worker：
- 评分公式：`proficiency * 0.4 + success_rate * 0.4 + (1/load) * 0.2`
- EWMA 更新（alpha=0.1）：每次执行后更新 `success_rate` 和 `avg_duration_ms`

### 4.11 Checkpoint & Rollback（NEW）

**描述**：Workflow Stage 成功后的状态快照，支持回溯。Realizes UJ-3。

**来源**：能力体系 §4（`workflow_checkpoint.rs`）。

#### FR-31: Checkpoint 创建

`Checkpoint` 结构体：
- `id, workflow_id, stage_id, created_at`
- `inputs, outputs`（序列化数据）
- `file_changes: Vec<FileChange>`（文件变更快照）
- `executor_worker, success, duration_ms`

**Consequences:**
- Stage 成功后自动创建（如果 `checkpoint: on_converge`）

#### FR-32: Rollback 执行

- `FileSystemOnly` — 只恢复文件

## 5. Non-Goals

- **不做 Agent 实现**：acp-swarm 不写代码、不写小说。
- **不绑定特定 Agent**：任何实现 Worker Protocol 的 Agent 都能接入。
- **不支持非编程领域**：v1 只聚焦编程。写小说/训练/游戏留给 v2+。
- **不提供 no-code 界面**：v1 需要会写代码。
- **不支持生产环境部署**：v1 是 MVP。
- **不支持跨机器联邦**：v1 单机部署。
- **不支持 Python SDK**：v1 只有 Rust + TypeScript。
- **不支持 Mesh/Pipeline/Hierarchical 拓扑**：v1 只有 Star + Chain。
- **不支持 Adversarial/Hybrid Evaluator**：v1 只有 Auto + Queen。
- **不支持 Skill 市场**：v1 不支持 Skill 共享。
- **不支持 HNSW 向量记忆**：v2+。
