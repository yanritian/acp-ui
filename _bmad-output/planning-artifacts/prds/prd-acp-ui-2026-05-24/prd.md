## 一、产品定位

### 1.1 核心价值

**ACP-UI = 跨平台异步 AI Agent 控制器**

```
ACP-UI 不是又一个 AI 编程工具。
它是 AI Agent 的操作系统 —— 管理多个 Agent 的协作、监控它们的性能、
让它们自我修复和进化。用户从"坐在电脑前"变成"随时随地控制"。
```

核心价值 =
  异步任务控制（手机/飞书/Telegram/Discord 随时审批）+
  Agent 驾驭层（Claude Code/Codex/Cursor 等已有 Agent 统一编排）+
  全平台 Bot 网关（富媒体卡片 + 操作按钮）+
  本地优先（所有数据执行存储在本机）+
  完全开源（社区驱动迭代）

### 1.2 差异化优势

| 优势 | 说明 | 对标竞品 |
|------|------|----------|
| **异步控制** | 飞书/手机/Telegram 随时审批，不坐在电脑前 | Claude Code/Cursor 都不支持 |
| **Agent 驾驭层** | 不做专业 Agent，而是驾驭 Claude Code/Codex/Cursor | 每个 Agent 都是独立工具 |
| **全平台 Bot** | 飞书/钉钉/微信/企微/Telegram/Discord 统一接入，富媒体回复 | 无竞品 |
| **本地优先** | SQLite 持久化，不依赖云端，本机即数字人 | OpenDevin 部分支持 |
| **完全开源** | 开源社区驱动，5元/月可选便利功能 | Cursor 商业收费 |

| 维度 | Claude Code | Cursor | Codex | **ACP-UI** |
|------|-------------|--------|-------|-----------|
| 交互方式 | 终端 | 编辑器 | Web | **自然语言 + 可视化面板** |
| Agent 数量 | 1 | 1 | 1 | **N（自动编排）** |
| 异步支持 | ❌ | ❌ | 部分 | **✅ 完整** |
| 跨平台 | 终端 | IDE | Web | **Tauri/Flutter/Web 全平台** |
| 持久记忆 | 无 | 无 | 无 | **SQLite + 向量** |
| Bot 接入 | 无 | 无 | 无 | **6 平台** |

### 1.3 竞品定位

ACP-UI 占据的是**"平台化、多 Agent、异步控制"**象限，目前没有直接竞争者。

```
                    ↑ 平台化程度
                    │
        ACP-UI  ●   │  （多 Agent 编排 + 异步控制）
                    │
     Qoder ●        │  Trae ●
     Cursor ●       │
     Claude Code ●  │
────────────────────┼────────────────────→ 异步支持程度
```

## 二、目标用户

### 2.1 用户画像

**主要用户：个人开发者 / 小团队**

| 特征 | 描述 |
|------|------|
| **角色** | 全栈开发者，独立开发者，小团队 leader |
| **痛点** | AI Agent 只能在电脑前使用，无法随时随地控制 |
| **场景** | 给 Agent 下任务后离开电脑，通过手机/飞书审批关键决策 |
| **期望** | 本地部署，隐私保护，驾驭多个 Agent |
| **规模** | 个人或小团队，无需企业级 SSO/SAML |

### 2.2 使用场景

| 场景 | 描述 |
|------|------|
| **异步开发** | 上午下任务，手机收到审批通知，点击批准，回家查看结果 |
| **碎片化决策** | 地铁上收到 Agent 提问，选择方案后继续执行 |
| **多 Agent 协作监控** | 电脑端看完整面板，手机端只做审批 |
| **Bot 远程控制** | 通过飞书/Telegram/Discord 发送任务、查看结果 |

### 2.3 用户旅程

**UJ-001: 异步开发流程**

```
1. 下任务 → 在电脑端给 Agent 下任务："帮我重构这个模块"
2. 离开 → Agent 开始执行，进度实时同步到所有端
3. 审批 → 手机收到通知："遇到 API 冲突，选方案 A 还是 B？"
4. 决策 → 点击选择方案 A，Agent 继续执行
5. 完成 → 晚上回家，电脑上查看完整结果和测试报告
```

**UJ-002: Bot 远程控制**

```
1. 发送指令 → 在飞书给 Bot 发："帮我实现登录功能，PRD 见附件"
2. Agent 分析 → Codex 分析 PRD，拆解子任务，生成执行计划
3. 计划展示 → 飞书卡片展示计划，用户点击 [批准执行]
4. 多 Agent 执行 → Claude Code 执行 UI 任务，Codex 执行 Auth 任务
5. 结果反馈 → 飞书原频道发送完成卡片 + 文件列表
```

### 2.4 成功指标

| 指标 | 目标值 | 验证方法 |
|------|--------|----------|
| **SM-001: 跨端同步延迟** | < 3 秒 | 电脑端下任务，手机端 3 秒内收到通知 |
| **SM-002: 审批响应时间** | 从通知到决策 < 30 秒 | 用户操作审批流程计时 |
| **SM-003: 构建质量** | 0 编译错误，236 测试全部通过 | `cargo check` + `npm test` |
| **SM-004: Bot 接入数量** | ≥ 1 平台完整接入 | 飞书 Bot 能发送富媒体卡片 |
| **SM-005: Agent 驾驭** | 能调度 Claude Code/Codex 执行真实任务 | 通过 `agent_orchestration` 执行 `claude --print -p "echo hello"` |

**反指标**:
- 同步延迟 > 10 秒 → 检查 Sync Engine 性能
- Bot 消息丢失 > 1% → 检查 Bot Gateway 重试机制

## 三、技术架构

### 3.1 分层架构

```
┌─────────────────────────────────────────────────────────────────┐
│                     用户接入层                                   │
│  Tauri Desktop │ Flutter Mobile │ Feishu │ Telegram │ Discord  │
└─────────────────────────────┬───────────────────────────────────┘
                              │
┌─────────────────────────────▼───────────────────────────────────┐
│                     Bot Gateway 层                               │
│  RichResponse 统一格式 │ 平台适配 │ 卡片转换 │ 按钮降级           │
└─────────────────────────────┬───────────────────────────────────┘
                              │
┌─────────────────────────────▼───────────────────────────────────┐
│                     核心引擎层（驾驭层）                          │
│  ├── Agent Orchestrator（能力注册/路由/CLI 执行/进程管理）         │
│  ├── Workflow Engine（DAG 工作流/阶段依赖/失败策略）               │
│  ├── Approval Engine（审批队列/回调通知/过期清理）                 │
│  ├── Sync Engine（SQLite 持久化/3 端同步/冲突解决）               │
│  └── 自我修复/进化引擎                                            │
└─────────────────────────────┬───────────────────────────────────┘
                              │
┌─────────────────────────────▼───────────────────────────────────┐
│                     执行层（专业 Agent）                          │
│  Claude Code CLI │ Codex CLI │ Cursor CLI │ 其他 CLI            │
└─────────────────────────────────────────────────────────────────┘
```

### 3.3 多端架构

| 端 | 技术栈 | 优先级 | 状态 |
|----|--------|--------|------|
| **Tauri Desktop** | Tauri 2 + Rust | P0 | ✅ 核心功能完成 |
| **Flutter Mobile** | Flutter 3.22+ | P0 | ✅ 极简重设计完成 |
| **Web** | Vue 3.5 + TypeScript | P0 | ✅ 编译通过 |

### 3.4 数据流

```
用户发送任务 → 渠道接收 → Bot Gateway 转换 → ACP 协议消息
    ↓
Agent Orchestrator 路由 → 选择最佳 Agent
    ↓
Spawn CLI 进程 → 实时监控进度 → 存储到 SQLite
    ↓
如需审批 → Approval Engine 创建请求 → 推送到所有渠道
    ↓
用户审批 → 回调恢复执行 → 结果整合 → 反馈用户
```

## 四、功能需求

### 4.1 核心功能（P0）

#### FR-001: Agent 驾驭层（驾驭已有 Agent）

**描述**: ACP-UI 不做专业 Agent，而是驾驭 Claude Code、Codex、Cursor 等已有 Agent。维护 Agent 注册表，根据能力路由任务，Spawn CLI 进程执行，实时捕获进度和结果。

**验收标准**:
- 能注册多个 Agent 及其能力标签
- 根据任务描述自动选择最佳 Agent
- Spawn CLI 进程并安全传参（无命令注入）
- 通过真实 PID 终止进程（非任务 ID）
- 超时处理自动 kill

**操作化验证**:
| 验证项 | 条件 | 测试方法 |
|--------|------|----------|
| 安全 CLI | 未知 CLI 被拒绝 | 注册 `evil-cli`，发送任务，期望被拒绝 |
| 真实执行 | `claude --print -p "echo hello"` 返回 "hello" | 通过 agent_orchestration 执行并捕获输出 |
| 正确取消 | cancel_task kill 真实子进程 | 启动任务后立即取消，验证进程终止 |

**依赖**: 无前置依赖

#### FR-002: 跨平台异步控制

**描述**: 用户可从任何渠道（Tauri Desktop、Flutter Mobile、飞书、Telegram、Discord、微信、企微）发送任务、查看进度、做审批。所有渠道共享同一会话上下文。

**验收标准**:
- 从飞书发送任务，Desktop 能看到进度
- 从手机审批，Desktop 同步结果
- 所有渠道使用 ACP 协议统一消息格式
- 传输层加密（TLS）

**操作化验证**:
| 验证项 | 条件 | 测试方法 |
|--------|------|----------|
| 跨端同步 | 飞书发送任务，Desktop < 3 秒收到 | 计时测试 |
| ACP 消息 | 加密消息能正确加解密 | encrypt/decrypt 测试 |

**依赖**: FR-001

#### FR-003: 异步审批协议

**描述**: 当 Agent 执行需要人类判断时，创建审批请求，可被任何渠道的任何人审批（批准/拒绝/加备注）。

**验收标准**:
- 审批请求持久化到 SQLite
- 回调通知机制
- 过期自动处理
- 支持 approve/reject/feedback 三种操作
- ApprovalDecision.option_id 正确存储

**操作化验证**:
| 验证项 | 条件 | 测试方法 |
|--------|------|----------|
| 持久化 | 应用重启后审批请求恢复 | 创建审批 → 重启 → 查询仍有效 |
| 回调 | 审批决策后回调触发 | 注册回调，审批后验证回调执行 |

**依赖**: FR-002

#### FR-004: Bot 网关层

**描述**: 统一 RichResponse 格式，适配 6 个平台。每个平台根据能力自动转换卡片、按钮、附件。

**验收标准**:
- 飞书：交互卡片 + 操作按钮（已实现）
- Telegram/Discord/钉钉/微信/企微：stub，supports_* 返回 false
- 不支持卡片的平台自动转换为文本

**操作化验证**:
| 验证项 | 条件 | 测试方法 |
|--------|------|----------|
| 飞书卡片 | RichResponse 转换为 FeishuCard | 测试 bot_gateway 飞书适配器 |
| 自动降级 | 不支持按钮的平台不显示按钮 | 验证 supports_buttons=false 的平台 |

**依赖**: FR-002

### 4.2 增强功能（P1）

#### FR-005: 本地优先持久化

**描述**: 所有数据持久化在本地 SQLite，不依赖云端。

**验收标准**:
- Sync Engine 使用 SQLite 存储（非内存）
- 应用重启后数据恢复
- FNV-1a checksum 验证数据完整性
- 冲突解决策略正常工作

**依赖**: 无

#### FR-006: 工作流定义 DSL

**描述**: 用户通过 JSON 定义多阶段工作流。

**验收标准**:
- JSON 解析和验证
- DAG 依赖解析
- 默认 8 阶段工作流模板
- 失败策略支持（abort/retry/fallback_to_manual/continue）

**依赖**: FR-001

#### FR-007: 推送通知

**描述**: 实时推送任务完成、审批请求、错误和进度里程碑。

**验收标准**:
- Tauri 桌面通知
- Web Push
- 通知包含标题、内容、操作按钮

**依赖**: FR-003

#### FR-008: ACP 协议

**描述**: 标准化消息格式，11 种消息类型，可选 AES-256-GCM 加密。

**验收标准**:
- 11 种消息类型
- 加密消息能正确加解密
- 大 payload 不栈溢出（chunked base64 编码）

**依赖**: 无

#### FR-009: Flutter 移动端极简设计

**描述**: 移动端三步骤：看进度、做审批、发指令。

**验收标准**:
- Progress 标签：进度仪表板 + 下拉刷新
- Approvals 标签：审批列表 + 滑动操作 + 真实 badge 计数
- Instructions 标签：类聊天界面 + 发送按钮响应

**操作化验证**:
| 验证项 | 条件 | 测试方法 |
|--------|------|----------|
| Badge 计数 | 显示真实待审批数量 | 创建 3 个审批 → badge 显示 "3" |
| 发送按钮 | 输入文字后按钮出现 | 在 TextField 中输入，按钮立即出现 |
| 失败任务 | 失败显示 0% 进度（非 100%） | 设置 failed 状态，验证进度条 |

**依赖**: FR-002, FR-003
