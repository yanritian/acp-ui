## 一、核心产品思考

### 1.1 为什么做"Terraform for AI Agents"？

**用户明确核心价值**: **提高效率**（自动编排多 Agent，比手动调用快 10x）

类比 Terraform 的核心逻辑：
- **Terraform**: 用户写一个配置文件（HCL），系统自动编排云资源创建（AWS/GCP/Azure）
- **ACP-UI**: 用户输入一句话，系统自动编排 Agent 执行（Claude Code/Kimi/可灵/WPS）

关键洞察：
```
传统 Terraform:
  用户写 HCL → Terraform 解析 → 资源依赖分析 → 并行创建 → 最终状态

ACP-UI:
  用户一句话 → Task Parser 解析 → Agent 依赖分析 → DAG 编排 → 结果汇总
```

### 1.2 用户角色动态识别（关键设计决策）

**用户明确要求**: 不是用户选择角色，而是系统自动识别

这是产品设计的关键洞察：
- **传统方式**: 用户手动选择角色（程序员/营销/财务），然后输入需求
- **新设计**: 用户输入一句话，系统根据内容自动识别角色

为什么这样设计？
1. **降低门槛**: 用户不需要先了解系统支持哪些角色
2. **更自然**: 用户直接表达需求，不需要思考"我是哪个角色"
3. **跨角色**: 用户可以在不同会话中扮演不同角色（例如：程序员在做营销视频）
4. **历史学习**: 系统可以学习用户偏好，提高识别准确率

### 1.3 透明决策机制（关键设计决策）

**用户明确要求**: 自动并且提供思路给用户

这是信任建立的关键：
- **不透明的 AI 系统**: 用户不知道为什么选择某个 Agent，不信任系统
- **透明的 ACP-UI**: 用户可以查看 Agent 选择理由、执行预估、DAG 可视化

展示内容：
1. **Agent 选择理由**: 能力匹配度 + 成本优化 + 假康状态
2. **执行预估**: 预估成本 + 执行时间 + 依赖关系
3. **实时 DAG 可视化**: 执行图 + 每个 Agent 状态
4. **执行结果详情**: 每个 Agent 输出 + 成本 + Token 用量

用户可操作：
- 确认执行
- 修改 Agent 选择
- 查看详情

## 二、用户场景深入分析

### 2.1 程序员场景扩展

**用户反馈**: 还能优化代码，甚至可以架构替换，语言替换，从顶层去解决历史遗留问题！

这扩展了程序员场景的深度：

| 传统代码 Agent | ACP-UI 扩展场景 |
|----------------|-----------------|
| 代码生成 | **架构替换**（MVC → 微服务） |
| Bug 修复 | **语言替换**（Java → Go） |
| 代码审查 | **老项目重构**（10 年前项目现代化） |

关键洞察：
- 程序员的需求不仅是"写代码"，还包括"重构架构"、"迁移语言"
- 这需要 Agent 组合：Claude Code (分析) → Codex (重构) → Architecture Advisor → Test Agent
- DAG 编排：分析 → 重构（并行）→ 测试验证

## 三、Orca 项目学习总结

### 3.1 araa47/orca: Agent DSL 设计

**学习点**: DSL 定义 Agent 行为和工作流

Orca 的 DSL 结构：
```yaml
agent:
  name: code-writer
  capabilities: [coding, debugging]
  config:
    timeout: 30m
    retry: 3
  
workflow:
  steps:
    - agent: code-writer
      action: write-code
      input: ${task.description}
    - agent: code-reviewer
      action: review
      depends_on: [code-writer]
```

应用到 ACP-UI：
- **Skill 定义格式**: YAML 格式定义 Agent 组合（见 PRD §3.4）
- **Agent 配置分离**: Agent 定义与工作流定义分离
- **依赖管理**: `depends_on` 字段表示执行顺序

### 3.2 ThakeeNathees/orca: Worktree 隔离

**学习点**: 每个任务独立 git worktree，实现执行隔离

Orca 的隔离机制：
```bash
# 为每个任务创建独立 worktree
git worktree add .orca/task-123

# 在 worktree 中执行
cd .orca/task-123
claude-code execute task-123

# 完成后清理
git worktree remove .orca/task-123
```

应用到 ACP-UI：
- **执行隔离**: 并发任务不互相干扰（程序员场景可能同时重构多个模块）
- **状态保存**: 每个 worktree 保存执行状态
- **回滚支持**: 失败后可回滚到干净状态

现有基础：
- `BranchLockManager` 已实现分支锁机制
- `SessionManager` 已支持 cwd 隔离
- **需要增强**: worktree 自动创建/清理

### 3.3 OpenOrca: Checkpoint 机制

**学习点**: 执行状态持久化，支持任务中断恢复

Orca 的 checkpoint：
```json
{
  "task_id": "task-123",
  "status": "in_progress",
  "current_step": 3,
  "total_steps": 5,
  "outputs": [
    { "step": 1, "output": "code-written" },
    { "step": 2, "output": "tests-passed" }
  ],
  "created_at": "2026-06-22T10:00:00Z"
}
```

应用到 ACP-UI：
- **任务中断恢复**: 长任务（如视频生成 3 分钟）中断后可恢复
- **进度可视化**: 用户实时看到进度（执行中/等待/完成）
- **失败分析**: 记录失败原因用于改进（Self-Healing）

现有基础：
- `GoalGraph` 已支持 Goal 状态持久化
- `ReconcileLoop` 已支持迭代记录
- **需要增强**: Agent 级别 checkpoint（Token 用量、中间输出）

### 3.4 AgentOrca: 可视化 DAG

**学习点**: 任务 DAG 实时可视化展示

Orca 的可视化：
- 实时展示 DAG 拓扑（节点 + 边）
- 每个节点显示状态（等待/执行/完成/失败）
- 点击节点查看详细输出
- 错误节点高亮并显示错误信息

应用到 ACP-UI：
- **Workflow Editor**: 用户自定义工作流可视化
- **执行监控**: 实时 DAG 执行可视化（用户要求透明决策）
- **错误定位**: 快速定位失败节点

现有基础：
- `PlanVisualization.vue` 已有基础
- `TaskGraphView.vue` 已有 DAG 可视化
- **需要增强**: Agent 级别节点展示 + Token 用量 + 成本

## 五、技术架构反思

### 5.1 为什么用 Rust Trait + TypeScript Interface？

**用户明确选择**: Rust Trait + TypeScript Interface（推荐）

双接口设计的原因：

| 场景 | Rust Trait | TypeScript Interface |
|------|------------|---------------------|
| **后端实现** | AgentAdapter trait，所有 Agent 实现统一接口 | 前端类型定义，调用 Tauri 命令 |
| **类型安全** | Rust 强类型，编译时检查 | TypeScript 类型，开发时检查 |
| **性能** | Rust 高性能，适合 CLI/API 调用 | 前端轻量，适合 UI 展示 |
| **跨语言** | Tauri 命令桥接 | 前端统一调用方式 |

### 5.2 为什么用 Agent Registry？

**能力匹配 + 成本优化 + 健康状态**

手动选择 Agent 的问题：
- 用户不知道哪个 Agent 最适合（能力匹配）
- 用户不知道哪个成本最低（成本优化）
- 用户不知道哪个健康（健康状态）

Agent Registry 的解决：
```rust
pub async fn select_optimal(&self, required: &[String], budget: f32) -> SelectionResult {
    // Step 1: 能力匹配（Jaccard 相似度 ≥ 0.3）
    let candidates = self.match_capabilities(required);
    
    // Step 2: 健康状态过滤（健康分数 ≥ 80，熔断器关闭）
    let healthy = self.filter_by_health(candidates);
    
    // Step 3: 成本优化排序（相似度优先，成本其次）
    let optimized = self.optimize_by_cost(healthy, budget);
    
    // Step 4: 生成决策解释（透明展示给用户）
    let explanation = self.generate_explanation(&optimized);
    
    SelectionResult { selected: optimized, reasoning: explanation }
}
```

### 5.3 为什么用 DAG Engine + Self-Healing？

**串行+并行混合执行 + 自动修复**

纯串行的问题：
- 效率低（可灵视频 3 分钟 + 即梦海报 30 秒，串行需要 3.5 分钟）

纯并行的问题：
- 无法处理依赖（Kimi 文案 → 可灵视频，视频依赖文案）

DAG Engine 的解决：
```
营销方案包 DAG:
  Kimi (文案) ──┬── 可灵 (视频) ──┬── Result Aggregator
                │                 │
                └── 即梦 (海报) ──┘

执行时间: 1 分钟（Kimi） + max(3 分钟可灵, 30 秒即梦) = 4 分钟
vs 串行: 1 + 3 + 0.5 = 4.5 分钟
节省 11% 时间
```

Self-Healing 的解决：
```
Agent 失败 → Loop Engine 检测异常 → 自动重试 → 失败后切换备用 Agent → 用户无感知

例如: 可灵 API 失败（网络错误）
  → Self-Healing 重试（3 次）
  → 仍然失败 → 切换备用视频生成 Agent（如果有）
  → 或降级（提示用户稍后再试）
```

### 5.4 为什么用 Token 追踪？

**用户明确要求**: 能查看 token 用量，token 追踪

成本失控的场景：
- 用户一句话触发多个 Agent（营销方案包：Kimi + 可灵 + 即梦）
- 不知道每个 Agent 用了多少 Token
- 不知道累计成本，可能超过预算

Token 追踪的解决：
```rust
pub struct CostTracker {
    token_usage: HashMap<String, TokenUsage>,  // taskId → TokenUsage
}

pub struct TokenUsage {
    input_tokens: u64,
    output_tokens: u64,
    total_tokens: u64,
    cost: f32,
}

// 实时展示给用户
UI: "Kimi: 输入 200 tokens, 输出 500 tokens, 成本 ¥0.008"
```

## 六、技术挑战与对策

### 6.1 用户角色识别准确性

**挑战**: 用户输入一句话，系统如何准确识别角色？

**对策**:
1. **关键词识别**: "营销方案" → 营销角色，"代码审查" → 程序员角色
2. **反问确认**: 系统不确定时，自然语言反问："我识别到您可能是程序员或营销人员，请问您当前是哪个角色？"
3. **历史学习**: 记录用户历史会话，学习用户偏好（例如：用户 80% 的时间是程序员角色）
4. **会话角色**: 用户可以在不同会话中手动切换角色

### 6.2 任务解析准确性

**挑战**: 用户一句话包含多个任务，系统如何准确解析？

**对策**:
1. **NLP 解析**: 使用 Kimi 或通义千问作为"任务解析器"，先解析用户意图
2. **规则匹配**: 预定义规则（例如："生成 X 并 Y" → 两个任务）
3. **多轮反问**: 如果解析不确定，系统反问用户确认
4. **透明展示**: 展示解析结果给用户，用户可修改

### 6.3 Agent 选择算法优化

**挑战**: 如何选择最优 Agent 组合（能力 + 成本 + 健康）？

**对策**:
1. **Jaccard 相似度**: 计算用户需求能力与 Agent 能力的匹配度
2. **成本优化**: 相同能力优先选择成本最低的 Agent
3. **健康状态**: 健康分数 ≥ 80，熔断器关闭的 Agent 才选择
4. **透明展示**: 展示选择理由给用户（能力匹配度 85%，成本最低 ¥0.5，健康分数 95%）

### 6.4 DAG 编排复杂度

**挑战**: 串行+并行混合执行，如何处理依赖和同步？

**对策**:
1. **依赖分析**: Agent A 的输出作为 Agent B 的输入 → A → B（串行）
2. **并行识别**: Agent B 和 Agent C 都依赖 Agent A，但彼此无依赖 → A → (B + C)（并行）
3. **同步点**: 所有并行 Agent 完成后，汇总结果 → SyncPoint
4. **可视化**: DAG 可视化展示给用户，用户可以看到执行流程

### 6.5 API 密钥管理

**挑战**: 不同 API 需要不同密钥，如何安全存储？

**对策**:
1. **加密存储**: SQLite 加密存储（使用系统密钥加密）
2. **用户授权**: 用户主动输入密钥，系统不自动获取
3. **不打印明文**: 日志中只显示 masked 密钥（例如："sk-proj-****"）
4. **定期提醒**: 提醒用户更新密钥（例如：密钥过期提醒）

### 6.6 API 成本失控

**挑战**: 用户一句话可能触发多个 API，成本失控。

**对策**:
1. **预算上限**: 用户设置月度预算上限（例如：¥100/月）
2. **预估确认**: 每次执行前显示预估成本，用户确认后执行
3. **实时追踪**: 执行中实时显示累计成本 + Token 用量
4. **熔断机制**: 超过预算自动熔断，停止执行
