## 二、Skill 体系 —— Worker 能力声明与动态路由

### 2.1 战略意图

当前 Skill 系统的问题是：Skill 存在于 ACP-UI 内部，Worker（Codex/Claude Code）不知道 Skill 的存在。蜂群模式下，**每个 Worker 需要声明自己"内置"了哪些 Skill，Orchestrator 据此路由任务。**

### 2.2 数据结构设计

**文件**: `src-tauri/src/swarm_skill_registry.rs`（新建）

```rust
//! Swarm Skill Registry - Worker 能力声明与 Skill 路由

use serde::{Deserialize, Serialize};
use std::collections::HashMap;

/// Worker 声明的 Skill（从 Worker 注册时获取）
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct WorkerSkill {
    /// Skill 名称（如 "code-review", "architecture-design", "test-generation"）
    pub name: String,
    /// Worker 自评估的熟练度（0.0-1.0）
    pub proficiency: f32,
    /// 历史执行次数
    pub execution_count: u64,
    /// 历史成功率
    pub success_rate: f32,
    /// 平均执行时间（毫秒）
    pub avg_duration_ms: u64,
    /// 该 Skill 是否需要特殊权限（如网络访问、文件写入）
    pub required_permissions: Vec<String>,
}

/// Worker 注册时提交的能力清单
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct WorkerCapabilityManifest {
    pub worker_id: String,
    pub worker_type: String,  // "codex", "claude-code", "gemini", "custom"
    pub skills: Vec<WorkerSkill>,
    /// 该 Worker 最大并发任务数
    pub max_concurrency: u32,
    /// 该 Worker 支持的最大上下文长度（tokens）
    pub max_context_tokens: u64,
    /// 该 Worker 的输出格式偏好
    pub output_formats: Vec<String>,  // ["structured", "markdown", "diff"]
}

/// Skill 路由决策
#[derive(Debug, Clone)]
pub struct SkillRouteDecision {
    pub target_worker: String,
    pub skill_name: String,
    pub confidence: f32,
    pub reason: String,  // "highest_proficiency", "lowest_load", "best_success_rate"
}

/// Swarm 级别的 Skill 路由表
pub struct SwarmSkillRouter {
    /// skill_name -> Vec<(worker_id, WorkerSkill)>
    routes: HashMap<String, Vec<(String, WorkerSkill)>>,
    /// worker_id -> 当前负载
    worker_load: HashMap<String, u32>,
}

impl SwarmSkillRouter {
    /// Worker 注册时更新路由表
    pub fn register_worker(&mut self, manifest: &WorkerCapabilityManifest) {
        for skill in &manifest.skills {
            self.routes
                .entry(skill.name.clone())
                .or_default()
                .push((manifest.worker_id.clone(), skill.clone()));
        }
        self.worker_load.insert(manifest.worker_id.clone(), 0);
    }

    /// 根据 Skill 名称路由到最佳 Worker
    pub fn route(&self, skill_name: &str) -> Option<SkillRouteDecision> {
        let candidates = self.routes.get(skill_name)?;
        
        // 过滤掉满载的 Worker
        let available: Vec<_> = candidates
            .iter()
            .filter(|(wid, _)| {
                self.worker_load.get(wid).copied().unwrap_or(u32::MAX) < 10
            })
            .collect();

        if available.is_empty() {
            return None;
        }

        // 按综合评分排序：proficiency * 0.4 + success_rate * 0.4 + (1/load) * 0.2
        let best = available
            .iter()
            .max_by(|(_, a), (_, b)| {
                let score_a = a.proficiency * 0.4 + a.success_rate * 0.4;
                let score_b = b.proficiency * 0.4 + b.success_rate * 0.4;
                score_a.partial_cmp(&score_b).unwrap()
            })?;

        Some(SkillRouteDecision {
            target_worker: best.0.clone(),
            skill_name: skill_name.to_string(),
            confidence: best.1.proficiency * best.1.success_rate,
            reason: "best_combined_score".to_string(),
        })
    }

    /// Skill 执行完成后更新统计
    pub fn record_execution(
        &mut self,
        worker_id: &str,
        skill_name: &str,
        success: bool,
        duration_ms: u64,
    ) {
        if let Some(entries) = self.routes.get_mut(skill_name) {
            for (wid, skill) in entries.iter_mut() {
                if wid == worker_id {
                    skill.execution_count += 1;
                    // 指数加权移动平均
                    let alpha = 0.1;
                    skill.success_rate = if success {
                        skill.success_rate * (1.0 - alpha) + alpha
                    } else {
                        skill.success_rate * (1.0 - alpha)
                    };
                    skill.avg_duration_ms =
                        (skill.avg_duration_ms as f64 * (1.0 - alpha) + duration_ms as f64 * alpha) as u64;
                }
            }
        }
    }
}
```

## 三、Tool 体系 —— 动态注册与权限管控

### 3.1 战略意图

当前 `tool-registry.ts` 已经有完善的 RiskClass/PermissionPolicy/SideEffects 模型，但它是**静态的**——所有 Tool 硬编码在前端。蜂群模式下：
- 每个 Worker 启动时**自动注册**自己可用的 Tool
- Orchestrator 根据 Tool 的 RiskClass 决定是否需要审批
- Tool 执行结果自动关联到 Worker 的 TaskShard

### 3.2 数据结构增强

**文件**: `src/lib/agent-runtime/tool-registry.ts`（增强现有文件）

在现有 `ToolSchema` 基础上新增：

```typescript
/// Worker 提供的 Tool 注册请求
export interface WorkerToolRegistration {
  workerId: string;
  tools: ToolSchema[];
}

/// Tool 执行审计记录
export interface ToolExecutionAudit {
  id: string;
  toolName: string;
  workerId: string;
  taskId: string;           // 关联的 TaskShard
  input: unknown;
  output?: unknown;
  riskClass: RiskClass;
  permissionUsed: PermissionPolicy;
  approvalId?: string;      // 如果走了审批
  startedAt: number;
  completedAt: number;
  success: boolean;
  error?: string;
}

/// 动态 Tool 注册表
export class DynamicToolRegistry {
  private tools: Map<string, ToolSchema & { providerWorker: string }> = new Map();
  private auditLog: ToolExecutionAudit[] = [];

  /// Worker 注册自己的 Tool
  registerWorkerTools(reg: WorkerToolRegistration): void {
    for (const tool of reg.tools) {
      this.tools.set(tool.name, { ...tool, providerWorker: reg.workerId });
    }
  }

  /// Worker 下线时注销 Tool
  unregisterWorkerTools(workerId: string): void {
    for (const [name, tool] of this.tools) {
      if (tool.providerWorker === workerId) {
        this.tools.delete(name);
      }
    }
  }

  /// 根据 RiskClass 判断是否需要审批
  needsApproval(toolName: string): boolean {
    const tool = this.tools.get(toolName);
    if (!tool) return true;  // 未知 Tool 默认需要审批
    return tool.permission === 'approval_required'
      || tool.permission === 'approval_strong_auth'
      || tool.permission === 'sandbox_required';
  }

  /// 执行 Tool（带审计）
  async executeTool(
    toolName: string,
    input: unknown,
    workerId: string,
    taskId: string,
  ): Promise<{ success: boolean; output: unknown; audit: ToolExecutionAudit }> {
    const tool = this.tools.get(toolName);
    if (!tool) throw new Error(`Unknown tool: ${toolName}`);

    const audit: ToolExecutionAudit = {
      id: `audit-${Date.now()}-${Math.random().toString(36).slice(2)}`,
      toolName,
      workerId,
      taskId,
      input,
      riskClass: tool.riskClass,
      permissionUsed: tool.permission,
      startedAt: Date.now(),
      completedAt: 0,
      success: false,
    };

    try {
      // 检查审批
      if (this.needsApproval(toolName)) {
        audit.approvalId = await requestApproval(toolName, input);
      }

      // 执行
      const output = await invokeOrProxy('execute_worker_tool', {
        workerId, toolName, input,
      });

      audit.output = output;
      audit.success = true;
      audit.completedAt = Date.now();
    } catch (e) {
      audit.error = String(e);
      audit.completedAt = Date.now();
    }

    this.auditLog.push(audit);
    return { success: audit.success, output: audit.output, audit };
  }

  /// 审计日志查询
  getAuditLog(filter?: { workerId?: string; taskId?: string; riskClass?: RiskClass }): ToolExecutionAudit[] {
    return this.auditLog.filter(a => {
      if (filter?.workerId && a.workerId !== filter.workerId) return false;
      if (filter?.taskId && a.taskId !== filter.taskId) return false;
      if (filter?.riskClass && a.riskClass !== filter.riskClass) return false;
      return true;
    });
  }
}
```

## 四、Workflow 体系 —— 蜂群感知的动态工作流

### 4.1 战略意图

当前 Workflow 和 Swarm 是割裂的。`workflow-dsl.ts` 定义了 8 个阶段（plan → design → implement → test → review → refine → deploy → verify），但这些阶段不知道哪个 Worker 在执行。目标：**Workflow 的每个 Stage 升级为一个 Goal（带完成条件 + 评估器），Orchestrator 根据 Goal 路由 Worker 并驱动 Reconcile Loop。**

> **核心升级**: Stage 不再是"执行完就走"，而是"循环迭代直到完成条件满足"。参考 Codex `/goal` 和 Claude Code `/goal` 的 Goal 驱动执行模型。

### 4.2 Workflow DSL 增强

**文件**: `src/lib/workflow/workflow-dsl.ts`（增强 `StageDefinition`）

```typescript
export interface StageDefinition {
  id: string;
  name: string;
  agentId?: string;
  capability?: string;
  inputs: string[];
  outputs: string[];
  timeout?: number;
  requiresApproval?: boolean;
  retryCount?: number;
  condition?: string;
  
  // === 新增：蜂群感知字段 ===
  /// 所需 Skill 名称（Orchestrator 根据此字段路由 Worker）
  requiredSkill?: string;
  /// 是否支持并行执行（同一 Stage 的多个实例并行）
  parallel?: boolean;
  /// 检查点策略：Stage 完成后是否创建检查点（用于回溯）
  checkpoint?: CheckpointPolicy;
  
  // === 新增：Goal 驱动字段（Codex /goal 模式） ===
  /// 完成条件 —— 什么算"这个 Stage 做完了"
  /// 替代 retryCount：不再是"重试 N 次"，而是"循环到条件满足"
  completionCondition?: GoalCompletionCondition;
  /// 评估器 —— 谁来验证完成条件（默认 Queen/Orchestrator）
  evaluator?: GoalEvaluator;
  /// Token 预算 —— 这个 Stage 最多消耗多少 Token
  tokenBudget?: number;
  /// 最大迭代轮数（防止无限循环）
  maxIterations?: number;
}

/// 完成条件类型
export type GoalCompletionCondition =
  | { type: 'command_success'; command: string; args?: string[] }   // 命令退出码为 0
  | { type: 'output_contains'; command: string; pattern: string }   // 输出包含特定文本
  | { type: 'output_matches'; command: string; regex: string }      // 输出匹配正则
  | { type: 'all'; conditions: GoalCompletionCondition[] }          // 所有条件满足
  | { type: 'any'; conditions: GoalCompletionCondition[] }          // 任一条件满足
  | { type: 'queen_judgment'; criteria: string };                   // Queen 主观判断

/// 评估器类型
export type GoalEvaluator =
  | 'auto'              // 自动运行 completionCondition 中的命令
  | 'queen'             // Queen（Orchestrator）判断
  | { type: 'adversarial'; workerId: string };  // 对抗性审查（另一个 Worker 评估）

export type CheckpointPolicy =
  | 'never'           // 不创建检查点
  | 'on_converge'     // Goal Converged 时创建（替代 on_success）
  | 'always'          // 无论 Converged 还是 Failed 都创建
  | 'on_approval';    // 审批通过后创建
```

### 4.3 检查点与回溯机制

**文件**: `src-tauri/src/workflow_checkpoint.rs`（新建）

```rust
//! Workflow Checkpoint & Rollback - 工作流回溯机制
//!
//! 每个检查点保存：
//! 1. 该 Stage 的输入和输出
//! 2. 文件系统的 diff（哪些文件被修改了）
//! 3. Worker 的上下文快照（可选）

use serde::{Deserialize, Serialize};
use std::collections::HashMap;
use std::path::PathBuf;
use chrono::{DateTime, Utc};

/// 检查点记录
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct Checkpoint {
    pub id: String,
    pub workflow_id: String,
    pub stage_id: String,
    pub created_at: DateTime<Utc>,
    
    /// Stage 输入数据
    pub inputs: serde_json::Value,
    /// Stage 输出数据
    pub outputs: serde_json::Value,
    
    /// 文件系统变更快照
    pub file_changes: Vec<FileChange>,
    
    /// 执行该 Stage 的 Worker
    pub executor_worker: String,
    
    /// Stage 执行结果
    pub success: bool,
    pub duration_ms: u64,
    
    /// 元数据（Worker token 消耗、Tool 调用次数等）
    pub metadata: HashMap<String, serde_json::Value>,
}

/// 文件变更记录
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct FileChange {
    pub path: PathBuf,
    pub change_type: FileChangeType,
    /// 变更前的内容 hash（用于验证回溯）
    pub before_hash: Option<String>,
    /// 变更前的内容备份（用于回溯恢复）
    pub before_content: Option<Vec<u8>>,
    /// 变更后的内容 hash
    pub after_hash: Option<String>,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub enum FileChangeType {
    Created,
    Modified,
    Deleted,
}

/// 回溯请求
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct RollbackRequest {
    pub workflow_id: String,
    /// 回溯到哪个检查点
    pub target_checkpoint_id: String,
    /// 回溯策略
    pub strategy: RollbackStrategy,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub enum RollbackStrategy {
    /// 只回滚文件系统（恢复文件内容）
    FileSystemOnly,
    /// 回滚文件系统 + 重新执行后续 Stage
    FileSystemAndRerun,
    /// 只回滚数据（不改文件系统，只恢复 Stage 的输入输出数据）
    DataOnly,
}

/// 回溯执行结果
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct RollbackResult {
    pub success: bool,
    pub rolled_back_checkpoint: String,
    pub files_restored: usize,
    pub files_failed: usize,
    pub stages_to_rerun: Vec<String>,  // 需要重新执行的 Stage ID
    pub errors: Vec<String>,
}
```

**Rust 回溯执行器核心逻辑**：

```rust
impl CheckpointManager {
    /// 创建检查点
    pub fn create_checkpoint(
        &self,
        workflow_id: &str,
        stage_id: &str,
        inputs: serde_json::Value,
        outputs: serde_json::Value,
        executor_worker: &str,
        success: bool,
        duration_ms: u64,
    ) -> Result<Checkpoint, String> {
        // 1. 扫描 cwd 获取文件 diff
        let file_changes = self.capture_file_changes(workflow_id)?;
        
        // 2. 构建检查点
        let checkpoint = Checkpoint {
            id: format!("cp-{}-{}", stage_id, chrono::Utc::now().timestamp()),
            workflow_id: workflow_id.to_string(),
            stage_id: stage_id.to_string(),
            created_at: chrono::Utc::now(),
            inputs,
            outputs,
            file_changes,
            executor_worker: executor_worker.to_string(),
            success,
            duration_ms,
            metadata: HashMap::new(),
        };
        
        // 3. 持久化到 SQLite
        self.persist_checkpoint(&checkpoint)?;
        
        Ok(checkpoint)
    }

    /// 执行回溯
    pub fn rollback(&self, request: RollbackRequest) -> Result<RollbackResult, String> {
        let target = self.get_checkpoint(&request.target_checkpoint_id)?;
        
        // 获取目标检查点之后的所有检查点（需要回滚的）
        let later_checkpoints = self.get_checkpoints_after(
            &request.workflow_id,
            &target.created_at,
        )?;
        
        let mut files_restored = 0;
        let mut files_failed = 0;
        let mut errors = vec![];
        
        // 逆序回滚（从最新的检查点开始恢复）
        for cp in later_checkpoints.iter().rev() {
            for change in &cp.file_changes {
                match self.restore_file(change) {
                    Ok(_) => files_restored += 1,
                    Err(e) => {
                        files_failed += 1;
                        errors.push(format!("Failed to restore {}: {}", change.path.display(), e));
                    }
                }
            }
        }
        
        let stages_to_rerun = match request.strategy {
            RollbackStrategy::FileSystemAndRerun => {
                later_checkpoints.iter().map(|cp| cp.stage_id.clone()).collect()
            }
            _ => vec![],
        };
        
        Ok(RollbackResult {
            success: files_failed == 0,
            rolled_back_checkpoint: request.target_checkpoint_id,
            files_restored,
            files_failed,
            stages_to_rerun,
            errors,
        })
    }
}
```

### 4.4 Workflow ↔ Swarm 桥接

**文件**: `src/lib/workflow/swarm-workflow-bridge.ts`（新建）

```typescript
import { invokeOrProxy } from '../host';
import type { WorkflowDefinition, StageDefinition } from './workflow-dsl';
import type { SkillRouteDecision } from '../types';

/**
 * SwarmWorkflowBridge - 将 Workflow 的 Stage 分发给蜂群 Worker
 *
 * 核心流程：
 * 1. 解析 Workflow 的每个 Stage
 * 2. 根据 Stage.requiredSkill 查询 SwarmSkillRouter
 * 3. 将 Stage 分配给路由返回的 Worker
 * 4. 管理 Stage 间的依赖和数据传递
 */
export class SwarmWorkflowBridge {
  /// 为 Workflow 的所有 Stage 预分配 Worker
  async planWorkerAssignment(
    workflow: WorkflowDefinition
  ): Promise<Map<string, SkillRouteDecision>> {
    const assignments = new Map<string, SkillRouteDecision>();

    for (const stage of workflow.stages) {
      if (stage.requiredSkill) {
        const decision = await invokeOrProxy('swarm_route_by_skill', {
          skillName: stage.requiredSkill,
        }) as SkillRouteDecision | null;

        if (decision) {
          assignments.set(stage.id, decision);
        }
      }
    }

    return assignments;
  }

  /// 执行单个 Stage（通过蜂群 Worker）
  async executeStageViaSwarm(
    stage: StageDefinition,
    workerId: string,
    inputData: unknown,
  ): Promise<{ output: unknown; checkpointId?: string }> {
    const result = await invokeOrProxy('swarm_execute_stage', {
      workerId,
      stageId: stage.id,
      input: inputData,
      timeout: stage.timeout,
    });

    // 如果需要创建检查点
    let checkpointId: string | undefined;
    if (stage.checkpoint && stage.checkpoint !== 'never') {
      const shouldCheckpoint =
        stage.checkpoint === 'always' ||
        (stage.checkpoint === 'on_success' && result.success) ||
        (stage.checkpoint === 'on_approval' && result.approved);

      if (shouldCheckpoint) {
        const cp = await invokeOrProxy('workflow_create_checkpoint', {
          stageId: stage.id,
          inputs: inputData,
          outputs: result.output,
          workerId,
          success: result.success,
        });
        checkpointId = cp.id;
      }
    }

    return { output: result.output, checkpointId };
  }

  /// 回溯到指定检查点
  async rollbackToCheckpoint(
    workflowId: string,
    checkpointId: string,
    strategy: 'file_system_only' | 'file_system_and_rerun' | 'data_only',
  ): Promise<{ success: boolean; filesRestored: number; stagesToRerun: string[] }> {
    return invokeOrProxy('workflow_rollback', {
      workflowId,
      targetCheckpointId: checkpointId,
      strategy,
    });
  }
}
```

### 4.5 验证步骤

1. 创建 Workflow：`plan`(requiredSkill: planning) → `implement`(requiredSkill: code-generation) → `test`(requiredSkill: test-generation) → `review`(requiredSkill: code-review)
2. `planWorkerAssignment` → plan 分配给 Claude Code，implement 分配给 Codex，test 分配给 Codex，review 分配给 Claude Code
3. 执行 implement Stage（checkpoint=on_success）→ 验证检查点创建
4. 执行 test Stage 失败 → 回溯到 implement 的检查点 → 验证文件恢复
5. 回溯后用 `file_system_and_rerun` 策略 → 验证 test 和 review 被标记为需要重新执行

## 五、Hook 体系 —— 蜂群级别的生命周期拦截

### 5.1 战略意图

当前 Hook 系统（`hooks_executor.rs`）只支持 PreToolUse/PostToolUse/Stop 三种粒度，作用域是单 Agent。蜂群模式需要新增：

- **PreTaskHook**: Worker 接收任务前拦截（可以修改任务参数、拒绝任务）
- **PostTaskHook**: Worker 完成任务后拦截（可以验证输出质量、触发后续动作）
- **PreStageHook / PostStageHook**: Workflow Stage 级别
- **SwarmLifecycleHook**: 蜂群整体生命周期（Worker 加入/离开/故障）

```typescript
export const WORKER_FAILOVER_HOOK = {
  name: 'worker-auto-failover',
  hookType: 'onWorkerError',
  scope: 'swarm',
  priority: 1,
  script: `
    // 当 Worker 连续 3 次失败，自动：
    // 1. 将该 Worker 标记为 Evicted
    // 2. 将其未完成的任务分配给 Replica Worker

        await invoke('swarm_reassign_tasks', { fromWorker: workerId });
        return { should_block: false, message: \`Worker \${workerId} evicted after \${errorCount} failures\` };
      }
      return { should_block: false };
    }
  `,
```

## 七、协议统一 —— ACP 协议规范

### 7.1 战略意图

ACP-UI 当前有多种通信方式并存：
- Tauri invoke（Rust ↔ TS）
- WebSocket（远程模式）
- stdio（CLI Agent 通信）
- HTTP（云端 API）

这些通信方式各有各的数据格式，导致同一个操作（如"提交任务"）在不同通道有不同的数据结构。**ACP 协议的目标是定义一套统一的消息格式，无论底层通道是什么，上层看到的都是同一种消息。**

### 7.2 ACP 消息格式

**文件**: `src/lib/acp-protocol/types.ts`（新建）

```typescript
/**
 * ACP Protocol v1 - Agent Communication Protocol
 *
 * 所有消息遵循统一格式：
 * { type, version, id, timestamp, payload }
 */

export const ACP_VERSION = '1.0';

/// ACP 消息基类
export interface AcpMessage {
  type: AcpMessageType;
  version: string;         // 协议版本（"1.0"）
  id: string;              // 消息唯一 ID
  timestamp: number;       // Unix 毫秒时间戳
  sourceId: string;        // 发送方 ID
  targetId?: string;       // 接收方 ID（空 = 广播）
  payload: unknown;        // 消息内容（具体结构由 type 决定）
  correlationId?: string;  // 关联 ID（用于请求-响应配对）
}

/// 消息类型
export type AcpMessageType =
  // Worker 生命周期
  | 'worker.register'          // Worker 注册
  | 'worker.heartbeat'         // Worker 心跳
  | 'worker.deregister'        // Worker 注销
  | 'worker.status'            // Worker 状态变更

  // 任务管理
  | 'task.submit'              // 提交任务
  | 'task.assign'              // 分配任务给 Worker
  | 'task.progress'            // 任务进度更新
  | 'task.result'              // 任务执行结果
  | 'task.cancel'              // 取消任务
  | 'task.fail'                // 任务失败

  // 蜂群协调
  | 'swarm.queen_elected'      // Queen 选举完成
  | 'swarm.queen_failover'     // Queen 故障切换
  | 'swarm.topology_change'    // 拓扑变更
  | 'swarm.rebalance'          // 任务重新分配

  // Workflow
  | 'workflow.start'           // 启动工作流
  | 'workflow.stage_start'     // Stage 开始
  | 'workflow.stage_complete'  // Stage 完成
  | 'workflow.stage_fail'      // Stage 失败
  | 'workflow.checkpoint'      // 检查点创建
  | 'workflow.rollback'        // 回溯请求

  // Tool 调用
  | 'tool.invoke'              // 调用 Tool
  | 'tool.result'              // Tool 返回结果
  | 'tool.approval_request'    // 请求审批
  | 'tool.approval_response'   // 审批响应

  // Hook
  | 'hook.trigger'             // Hook 触发
  | 'hook.result'              // Hook 执行结果

  // 系统
  | 'system.ping'              // 连通性检查
  | 'system.pong'              // 连通性响应
  | 'system.error'             // 系统错误
```

### 7.3 协议适配器

**文件**: `src/lib/acp-protocol/adapters.ts`（新建）

```typescript
/**
 * ACP 协议适配器 - 将不同底层通道统一为 AcpMessage
 */

/// 适配器接口
export interface AcpAdapter {
  /// 发送 ACP 消息
  send(message: AcpMessage): Promise<void>;
  /// 接收 ACP 消息（回调模式）
  onMessage(handler: (message: AcpMessage) => void): void;
  /// 关闭连接
  close(): Promise<void>;
}

/// Tauri Invoke 适配器
export class TauriAdapter implements AcpAdapter {
  async send(message: AcpMessage): Promise<void> {
    await invoke('acp_handle_message', { message });
  }

  onMessage(handler: (message: AcpMessage) => void): void {
    // 监听 Tauri 事件
    listen('acp-message', (event) => {
      handler(event.payload as AcpMessage);
    });
  }

  async close(): Promise<void> {
    // Tauri 不需要显式关闭
  }
}

/// Stdio 适配器（用于 CLI Agent 通信）
export class StdioAdapter implements AcpAdapter {
  private process: ChildProcess | null = null;

  constructor(command: string, args: string[]) {
    this.process = spawn(command, args, { stdio: ['pipe', 'pipe', 'pipe'] });
  }

  async send(message: AcpMessage): Promise<void> {
    const json = JSON.stringify(message) + '\n';
    this.process?.stdin?.write(json);
  }

  onMessage(handler: (message: AcpMessage) => void): void {
    let buffer = '';
    this.process?.stdout?.on('data', (data) => {
      buffer += data.toString();
      const lines = buffer.split('\n');
      buffer = lines.pop() || '';
      for (const line of lines) {
        if (line.trim()) {
          try {
            handler(JSON.parse(line) as AcpMessage);
          } catch {
            // 非 JSON 行，忽略
          }
        }
      }
    });
  }

  async close(): Promise<void> {
    this.process?.kill();
  }
}

/// WebSocket 适配器（用于远程模式）
export class WebSocketAdapter implements AcpAdapter {
  private ws: WebSocket | null = null;

  constructor(url: string) {
    this.ws = new WebSocket(url);
  }

  async send(message: AcpMessage): Promise<void> {
    this.ws?.send(JSON.stringify(message));
  }

  onMessage(handler: (message: AcpMessage) => void): void {
    this.ws?.addEventListener('message', (event) => {
      handler(JSON.parse(event.data) as AcpMessage);
    });
  }

  async close(): Promise<void> {
    this.ws?.close();
  }
}

/// HTTP 适配器（用于云端 API）
export class HttpAdapter implements AcpAdapter {
  constructor(private endpoint: string, private apiKey: string) {}

  async send(message: AcpMessage): Promise<void> {
    await fetch(`${this.endpoint}/acp/message`, {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json',
        'Authorization': `Bearer ${this.apiKey}`,
      },
      body: JSON.stringify(message),
    });
  }

  onMessage(handler: (message: AcpMessage) => void): void {
    // HTTP 使用轮询或 SSE
    const eventSource = new EventSource(`${this.endpoint}/acp/events`);
    eventSource.onmessage = (event) => {
      handler(JSON.parse(event.data) as AcpMessage);
    };
  }

  async close(): Promise<void> {
    // 关闭 SSE
  }
}
```

### 7.4 Rust 端 ACP 消息总线

**文件**: `src-tauri/src/acp_bus.rs`（新建，替代现有的 `agent_bus.rs`）

```rust
//! ACP Message Bus - 统一消息总线
//!
//! 所有消息（无论来自 Tauri invoke、stdio、WebSocket 还是 HTTP）
//! 都通过此消息总线路由。

use serde::{Deserialize, Serialize};
use std::collections::HashMap;
use std::sync::Arc;
use tokio::sync::{broadcast, RwLock};

/// ACP 消息（Rust 版本，与 TS 版本对齐）
#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(rename_all = "camelCase")]
pub struct AcpMessage {
    pub r#type: String,
    pub version: String,
    pub id: String,
    pub timestamp: u64,
    pub source_id: String,
    pub target_id: Option<String>,
    pub payload: serde_json::Value,
    pub correlation_id: Option<String>,
}

/// 消息总线
pub struct AcpMessageBus {
    /// 全局广播通道
    broadcast: broadcast::Sender<AcpMessage>,
    /// 订阅者注册表（target_id → sender）
    subscribers: Arc<RwLock<HashMap<String, broadcast::Sender<AcpMessage>>>>,
}

impl AcpMessageBus {
    pub fn new() -> Self {
        let (tx, _) = broadcast::channel(1024);
        Self {
            broadcast: tx,
            subscribers: Arc::new(RwLock::new(HashMap::new())),
        }
    }

    /// 发送消息（路由到目标）
    pub async fn send(&self, message: AcpMessage) -> Result<(), String> {
        if let Some(target) = &message.target_id {
            // 定向消息：发给特定订阅者
            let subs = self.subscribers.read().await;
            if let Some(sender) = subs.get(target) {
                sender.send(message.clone()).map_err(|e| e.to_string())?;
            }
        }
        // 同时广播（用于监控/日志）
        let _ = self.broadcast.send(message);
        Ok(())
    }

    /// 订阅特定 target_id 的消息
    pub async fn subscribe(&self, target_id: &str) -> broadcast::Receiver<AcpMessage> {
        let (tx, rx) = broadcast::channel(256);
        self.subscribers.write().await.insert(target_id.to_string(), tx);
        rx
    }

    /// 订阅所有消息（用于监控）
    pub fn subscribe_all(&self) -> broadcast::Receiver<AcpMessage> {
        self.broadcast.subscribe()
    }
}
```

### 7.5 验证步骤

1. **协议一致性**: 通过 Tauri invoke 发送 `task.submit` → 通过 WebSocket 发送同一消息 → Rust 端收到的 `AcpMessage` 结构完全一致
2. **适配器切换**: 注册一个 Worker 用 `StdioAdapter`（本地 CLI），另一个用 `HttpAdapter`（云端 API） → 两个 Worker 都能正常接收任务和返回结果
3. **消息路由**: 发送 `target_id = "worker-codex"` 的消息 → 只有 Codex Worker 收到
4. **广播监控**: SwarmDashboard 订阅全局广播 → 能实时看到所有消息流

## 九、给 GLM5 的执行纪律

1. **严格按 Phase 顺序执行**。Phase A 没完成不碰 Phase B。每个 Phase 完成后 commit 一次。
2. **每写一个 Rust 模块就跑 `cargo check`**。每写一个 TS 文件就跑 `npx vue-tsc --noEmit`。不要攒到最后一起验证。
3. **不要创建文档文件**。代码就是最好的文档。所有类型定义、接口签名、注释就是文档。
4. **不要"顺便"优化现有代码**。`bot_gateway.rs` 和 `hermes_traits.rs` 不要碰，即使它们看起来很碍眼。
5. **测试必须在对应 Phase 内写完**。不要"先写功能后补测试"——测试和功能一起 commit。
6. **Checkpoint 的回溯必须真的恢复文件**。不能只记录日志不恢复。测试必须验证文件内容被还原。
7. **ACP 协议的消息格式必须 TS 和 Rust 完全对齐**。用 JSON Schema 验证。TS 端发送的消息 Rust 端必须能正确反序列化，反之亦然。
8. **所有新增的 Tauri command 必须在 `lib.rs` 中注册**。不要出现"后端有 command 但前端调不到"的情况。
