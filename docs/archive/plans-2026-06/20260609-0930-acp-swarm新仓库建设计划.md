## 一、仓库定位与差异化

### 1.1 acp-swarm 是什么

**一句话**: 异构 Agent 蜂群的编排引擎，ACP 协议的参考实现。

**类比**: 如果说 Codex/Claude Code/Gemini 是单个"士兵"，acp-swarm 就是"参谋部 + 通讯连 + 后勤部"——它不直接打仗，但它决定谁去打、怎么配合、出了问题怎么救。

### 1.2 与原 acp-ui 的关系

| 维度 | acp-ui（原仓库） | acp-swarm（新仓库） |
|------|-----------------|-------------------|
| 定位 | ACP 客户端（UI 为主） | ACP 编排引擎（协议+调度为主） |
| 核心用户 | 开发者日常使用 | 开发者 + AI 平台集成方 |
| 技术重心 | Vue/Flutter UI、多平台适配 | Rust 编排引擎、协议规范、分布式调度 |
| README 第一句话 | "A modern cross-platform ACP client" | "Heterogeneous Agent Swarm Orchestrator" |
| Star 吸引力 | UI 截图、功能丰富 | 技术深度、设计理念、能跑的 demo |

## 三、Cargo Workspace 设计

新仓库的 Rust 端采用 Cargo Workspace，将单体 `src-tauri` 拆分为独立 crate：

```toml
# Cargo.toml（workspace 根）
[workspace]
members = [
    "crates/acp-core",
    "crates/acp-transport",
    "crates/swarm-engine",
    "crates/workflow-engine",
    "crates/hook-runtime",
    "crates/tool-sandbox",
    "crates/acp-cli",
    "src-tauri",
]
resolver = "2"

[workspace.dependencies]
serde = { version = "1", features = ["derive"] }
serde_json = "1"
tokio = { version = "1", features = ["full"] }
chrono = { version = "0.4", features = ["serde"] }
uuid = { version = "1", features = ["v4"] }
rusqlite = { version = "0.31", features = ["bundled"] }
thiserror = "1"
tracing = "0.1"
```

### crate 依赖关系

```
acp-core          ← 零内部依赖（纯类型 + 序列化 + 工具函数）
  ↑
acp-transport     ← 依赖 acp-core（传输层：stdio/WS/HTTP）
  ↑
swarm-engine      ← 依赖 acp-core + acp-transport（编排引擎）
workflow-engine   ← 依赖 acp-core + acp-transport（工作流 + 检查点）
hook-runtime      ← 依赖 acp-core（Hook 执行）
tool-sandbox      ← 依赖 acp-core（权限 + 沙箱）
  ↑
acp-cli           ← 依赖所有 crate（CLI 入口）
src-tauri         ← 依赖所有 crate（Tauri 壳）
```

每个 crate 都可以**独立编译和测试**，不依赖 Tauri。这是与 acp-ui 最大的架构差异——业务逻辑不再被 Tauri State 绑架。

## Key Features

- **Goal-Driven Execution** — Define completion conditions, not tasks. Workers iterate until goals converge (inspired by Codex `/goal`)

## 七、关键决策记录

### 7.1 为什么用 Cargo Workspace 而不是单体 crate？

单体 crate（acp-ui 现状）的问题：所有代码编译在一起，改一行数据库代码要重编整个项目（1600 行 websocket.rs 也在编译范围内）。Workspace 让每个 crate 独立编译，改动 `acp-core` 不需要重编 `swarm-engine`。

更重要的是：独立 crate 意味着**可以被其他项目引用**。未来有人想基于 acp-swarm 的协议层做自己的编排器，直接 `cargo add acp-core` 就行，不需要引入整个 Tauri 依赖。

### 7.2 为什么 Tauri 保留为薄壳？

Tauri 是 UI 壳，不是业务逻辑的容器。所有编排逻辑在 crates/ 里，Tauri 只做一件事：把 Rust 函数暴露给前端。这样 acp-cli 也能调用同样的 crates/ 而不需要 Tauri。

### 7.3 为什么不用 orphan branch 而是 fork + 清理？

orphan branch 会丢失 git 历史。fork + 清理保留了有价值的基础设施代码（host/index.ts, acp-bridge.ts, transport/ 等）的提交记录。后续如果要 upstream 同步 acp-ui 的 bugfix，fork 关系让 cherry-pick 更方便。

### 7.4 为什么 RFC 而不是普通 docs？

RFC（Request for Comments）是开源社区的标准设计文档格式。Kubernetes、Rust、React 的重大特性都用 RFC 推动。它传达的信号是"这是一个经过深思熟虑的设计，欢迎你参与讨论"，而不是"这是我的计划文档"。

## 八、给 GLM5 的执行纪律

1. **Phase 0 只做仓库初始化和文件搬运**。不要写任何新代码。
2. **Phase 1 的验证标准是 `cargo check --workspace` 和 `cargo test --workspace` 全过**。不是"大概能编译"，是零 error 零 warning。
3. **Phase 2 的验证标准是 `npx vue-tsc --noEmit` 和 `npx vitest run` 全过**。删除 orphan 文件后不能有 broken import。
4. **Phase 3 的验证标准是：能注册 Codex 和 Claude Code（用 echo 模拟），提交一个 Goal（带完成条件），蜂群并行执行 Reconcile Loop，Queen 评估 Converged，UI 显示结果**。这是整个项目的 proof of concept。
5. **每个 Phase 完成后 commit 一次**。commit message 格式：`<type>: <description>`（feat/refactor/test/docs/chore）。
6. **不要创建任何不在本计划中的文件**。没有 `utils.rs`，没有 `helpers.ts`，没有 `common/`。
7. **每个 crate 的 `lib.rs` 不超过 200 行**。超过就拆文件。
8. **Rust 代码 `#![deny(dead_code, unused_imports)]`**。编译有死代码或未使用的 import 就是 bug。
