# 游戏开发 Agent 产品契约

## 1. 产品定位

Hermes Game Operator 是一个面向游戏开发团队的可控 Agent 工作台。它不把 Agent 当作只能一次性输出答案的聊天机器人，而把 Agent 当作可以被观察、暂停、修改、审批、恢复和审计的执行者。

首个领域只做游戏开发，优先支持 Godot。运营、企业办公、传统开发、视频和漫画创作是后续领域包，不得在游戏闭环未成立前分散核心运行时。

## 2. 核心用户

### 操作员

负责定义目标、选择项目、检查计划、暂停执行、修改任务、审批风险动作和观察结果。操作员始终拥有取消、暂停和拒绝权限。

### 游戏开发者

关注项目文件、场景、脚本、资源、运行结果、测试结果和补丁差异，不需要理解 Agent 内部调度细节。

### 团队负责人

关注任务进度、阻塞原因、成本、变更风险、审计记录、成员权限和最终结果。

### Agent

负责理解目标、建立计划、调用 Skill/MCP/Hook、生成补丁、等待审批、执行验证和汇报证据；Agent 没有绕过权限的能力。

## 3. 第一版必须支持的用户故事

1. 操作员填写 Godot 项目路径和目标，创建一个 `game.godot` 任务。
2. Agent 扫描项目，返回结构化计划、涉及文件、风险和预计验证方式。
3. 操作员可以在计划阶段暂停，并修改目标、约束或某一个计划步骤。
4. Agent 生成可审阅补丁，界面显示文件级 diff、风险等级和验证命令。
5. 高风险补丁必须进入审批队列；拒绝后任务不能继续应用。
6. 操作员批准后 Agent 应用补丁，执行格式检查、脚本检查和 Godot 运行验证。
7. 任务在运行中可以被暂停、恢复或停止；停止必须产生审计事件。
8. 页面显示任务状态、事件时间线、执行计划、记忆摘要、当前阻塞和预计走向。
9. 操作员从 Web、Tauri、VSCode 或 IDEA 执行同一任务时，结果和权限一致。
10. 远程访问者必须经过身份认证、权限校验、审计和超时控制。

## 4. 不属于第一版的内容

- 不同时实现 Unity、Unreal、Ren'Py、视频、漫画和企业工作流的完整领域逻辑。
- 不让 Agent 直接拥有机器级管理员权限。
- 不把“自动生成一大堆文件”当成产品完成度。
- 不实现无法测试的全自动长期自主运行。
- 不为了追求多模型接入而牺牲事件、审批和恢复的一致性。

## 5. 产品原则

- **可控优先**：任何不可逆或高影响动作都必须可预览、可拒绝、可回滚。
- **证据优先**：每个成功结论都必须绑定日志、测试、diff、截图或运行结果。
- **事件优先**：界面状态由事件和服务端快照驱动，不由各客户端自行猜测。
- **协议优先**：Web、Tauri、VSCode、IDEA 不能各自发明一套 API。
- **领域包优先**：通用 Agent Runtime 与 Godot 工具分离，未来才能扩展其他领域。
- **人工随时介入**：暂停、修改、审批和停止不是异常流程，而是正常工作流。

## 6. 关键成功指标

| 指标 | 目标 |
|---|---|
| 任务状态一致性 | 多客户端读取同一任务时状态、版本和事件顺序一致 |
| 暂停响应 | 正常执行期间收到暂停后，5 秒内进入 `paused` 或返回明确阻塞原因 |
| 审批安全 | 没有审批记录时，高风险补丁不能进入 apply |
| 恢复可靠性 | 进程重启后能恢复任务快照、事件和待审批项 |
| 补丁可追溯 | 每次 apply 都能找到原始 diff、审批人、时间和验证结果 |
| 多语言完整性 | 13 个 Web locale 的 key 集合一致，无新增硬编码用户文案 |
| 客户端一致性 | Web、Tauri、VSCode、IDEA 使用同一协议和错误码 |
