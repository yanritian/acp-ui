# 游戏开发首个领域包：Godot

## 1. 领域边界

通用 Agent Runtime 只知道“调用能力并处理结果”，不知道 Godot 场景、节点、资源和脚本语义。Godot 领域包负责识别项目、读取规则、选择工具、生成验证计划和解释结果。

第一版固定支持 Godot 项目，识别依据是项目目录中存在 `project.godot`。Unity、Unreal、Ren'Py 只能作为未来领域包，不得在 Godot 规则中硬编码兼容分支。

## 2. Godot 项目检查流程

任务开始后按以下顺序执行只读检查：

1. 解析 `project.godot`，读取引擎版本、主场景、脚本语言和输入映射。
2. 生成项目目录摘要，排除 `.godot`、导入缓存、构建产物和秘密文件。
3. 检查项目是否在允许的路径边界内。
4. 检查当前 Git 状态、未提交变更和锁文件。
5. 搜索项目规则文件、README、贡献指南和测试命令。
6. 识别目标场景、相关脚本、资源引用和可能受影响的自动加载器。
7. 输出 `ProjectInspection`，包含证据路径和风险，而不是只返回自然语言。

## 3. 领域能力

每个能力必须登记为 Skill 或 MCP 工具，并声明输入 schema、输出 schema、风险等级、可取消性、是否需要审批和验证器。

| 能力 | 默认风险 | 必须验证 |
|---|---:|---|
| 读取项目结构 | low | 路径边界、忽略目录 |
| 读取脚本/场景/资源 | low | 文件存在、编码、大小上限 |
| 搜索符号和引用 | low | 查询超时、结果数量上限 |
| 生成计划 | low | 计划包含文件、风险和验证命令 |
| 修改 GDScript/C# | medium | diff、格式、静态检查 |
| 修改 `.tscn`/`.tres` | high | 结构解析、引用完整性、审批 |
| 修改项目设置 | high | 变更白名单、审批、备份 |
| 运行 Godot headless | medium | 命令白名单、超时、日志截断 |
| 启动编辑器或游戏 | high | 明确目标、进程回收、审批 |
| 删除或批量重命名 | critical | 二次确认、备份、回滚测试 |

## 4. 补丁规则

- 优先使用结构化编辑器处理 `.tscn`、`.tres` 和 JSON，不使用脆弱的正则替换。
- 文本补丁必须包含 old hash、new hash、上下文、目标文件和生成原因。
- 每次只应用一个逻辑补丁，补丁前自动生成备份或可逆快照。
- 应用前重新读取文件 hash；发现外部修改就进入 `PATCH_HASH_MISMATCH`。
- 补丁结果必须写入事件、审计和 checkpoint。

## 5. Godot 验证套餐

至少提供以下可配置验证器：

```text
godot --headless --path <project> --editor --quit
godot --headless --path <project> --path <project> --quit
godot --headless --path <project> --check-only
godot --headless --path <project> --script <test-script>
```

实际命令必须根据项目 Godot 版本和仓库规则生成，不能在没有确认可执行文件的情况下假装运行成功。每个验证器返回：退出码、耗时、stdout/stderr 路径、摘要、失败分类和可复现命令。

## 6. 首个真实闭环

固定准备一个最小 Godot fixture，至少包含：

- `project.godot`
- 一个主场景
- 一个玩家脚本
- 一个可测试的小目标，例如为玩家增加二段跳
- 一个失败前的基线验证
- 一个可审阅的预期 diff

闭环必须证明：扫描 -> 计划 -> 审批 -> 补丁 -> headless 验证 -> 运行结果 -> 记忆摘要 -> 最终事件。只在 Vue 中填表或只在 mock API 中改变状态，不算领域闭环。

## 7. 游戏任务记忆

Godot 领域记忆至少记录：引擎版本、项目根路径、主场景、脚本目录、输入动作、验证命令、常见失败原因和项目专属规则。每一条记忆必须带来源路径或执行事件，模型猜测不能直接进入永久记忆。
