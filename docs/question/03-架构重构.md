# ACP-UI 架构重构方案

> 本文聚焦**为功能服务的架构重构**——每项重构都要说清楚"改完以后能实现什么新功能、解决什么现有瓶颈"。
> 日期: 2026-06-05

---

## 重构总览

```
当前架构问题 → 重构动作 → 解锁的功能能力

会话 Store 33KB 巨型文件 → 按职责拆分为 4 个 Store → 支持独立模块（权限引擎、消息搜索、会话分析）
25 个平铺路由无分组 → 按领域分层路由 + 导航分组 → 支持功能模块按需加载、实验功能独立上下架
42 个组件平铺 → 按领域目录化 → 支持组件复用、功能模块独立打包
Plugin 系统 TS+Rust 双轨 → 统一 Plugin Protocol → 支持第三方插件生态、功能热插拔
Flutter+Tauri 双移动端 → 选定单一方案 → 移动端功能对齐、减少一半维护成本
```

## 一、会话 Store 拆分（`src/stores/session.ts` → 4 个 Store）

### 当前状态

`session.ts` 约 33KB，包含：
- 会话生命周期（create/resume/disconnect/cancel）
- 消息管理（CRUD、持久化、watch 保存）
- 权限请求处理
- 认证方法选择
- 模式/命令/模型管理
- 启动进度追踪
- 重连逻辑
- stderr 监听

### 为什么必须拆

**当前瓶颈**：任何一个模块的修改都需要理解整个 33KB 文件。新增"消息全文搜索"功能时，开发者需要绕过消息管理与会话生命周期的耦合。

**拆完后解锁的功能**：
- 消息搜索服务独立运行（不依赖会话连接状态）
- 权限引擎可独立测试、独立演进为规则引擎
- 会话分析面板（统计数据：总 token 用量、响应时间分布等）
- 多窗口同时打开多个会话（每条会话独立的状态管理）

### 拆分方案

```
stores/
├── session-lifecycle.ts    ← 会话生命周期（创建、恢复、断开、重连、取消）
│   职责: 管理当前连接状态、启动进度、stderr 流
│   暴露: createSession(), resumeSession(), disconnect(), reconnect()
│         isConnected, isConnecting, isReconnecting, startupPhase, startupLogs
│
├── session-messages.ts     ← 消息管理（收发、持久化、搜索）
│   职责: 消息 CRUD、KVStore 持久化、全文搜索索引
│   暴露: messages, sendMessage(), addMessage(), searchMessages()
│         saveMessages(), loadMessages()
│
├── session-permissions.ts  ← 权限与认证
│   职责: 权限请求队列、自动规则匹配、认证方法选择
│   暴露: pendingPermission, pendingAuthMethods
│         resolvePermission(), cancelPermission()
│         addPermissionRule(), getPermissionRules()
│
└── session-capabilities.ts ← Agent 能力管理
    职责: 模式列表、命令列表、模型列表
    暴露: availableModes, currentModeId, availableCommands, availableModels
           setMode(), setModel()
```

### 功能收益

| 重构前 | 重构后 |
|--------|--------|
| 无法在非聊天页查看消息 | `session-messages.ts` 独立运作，任何页面可引用 |
| 权限只有"批准/拒绝"两种操作 | 独立权限 Store 可扩展规则引擎、白名单/黑名单 |
| 无法做消息搜索 | 消息 Store 独立后可加全文索引 |
| 多会话需通过 MultiSessionStore 间接管理 | 每个会话独立 MessageStore 实例 |

## 三、Plugin 系统统一（TS Skill 系统 + Rust Plugin → 统一 Plugin Protocol）

### 当前状态

```
Rust 端:  plugin_registry.rs    ← Plugin trait + PluginRegistry
           hooks_executor.rs     ← Hook 执行器
           skill_commands.rs     ← Skill 的 Tauri 命令
           mcp_manager.rs        ← MCP 服务器管理

TS 端:    src/lib/skill-system/  ← Skill 类型 + SkillInvoker
           src/lib/plugin-system/ ← PluginService + SwarmService + WorkflowService
```

两套系统各自独立，没有共享的类型定义，没有统一的注册/发现/调用协议。

### 为什么必须统一

**当前瓶颈**：如果要新增一个"代码审查"能力——到底应该作为 Rust Plugin、TS Skill、还是 MCP Server？三种方式的注册、配置、调用方式完全不同。

**统一后解锁的功能**：
- 第三方开发者可以只用 TypeScript 写插件（不需要懂 Rust）
- 插件可以在运行时热加载/卸载，不需要重启应用
- 插件市场：统一的上架、评分、安装流程
- 能力发现：Agent 可通过统一协议查询所有可用能力

### 重构方案

**第一步：定义统一的 Plugin Manifest**

```typescript
// src/lib/plugin-protocol/types.ts  （共享类型，TS + Rust 各实现一遍）

interface PluginManifest {
  id: string;                    // 唯一标识，如 "skill.code-review"
  kind: 'skill' | 'mcp' | 'hook' | 'adapter' | 'cli-extension';
  name: string;                  // 人类可读名称
  version: string;               // 语义化版本
  description: string;
  capabilities: string[];        // 提供的能力列表（如 "code_review", "lint"）
  config: Record<string, unknown>; // 插件配置项 schema
  entry: {
    type: 'wasm' | 'typescript' | 'mcp-server' | 'binary';
    path?: string;               // TS/WASM 模块路径
    command?: string;            // binary/mcp-server 的命令
  };
}

interface PluginInstance {
  manifest: PluginManifest;
  state: 'loaded' | 'active' | 'error' | 'disabled';
  activate(): Promise<void>;
  deactivate(): Promise<void>;
  invoke(method: string, params: unknown): Promise<unknown>;
}
```

**第二步：Rust 端实现 PluginHost**

```rust
// src-tauri/src/plugin_host.rs

pub struct PluginHost {
    registry: PluginRegistry,       // 现有
    runtime: PluginRuntime,         // 新: 管理插件生命周期
    bridge: PluginBridge,           // 新: TS↔Rust 通信
}
```

**第三步：TS 端实现 PluginLoader**

```typescript
// src/lib/plugin-system/plugin-loader.ts

class PluginLoader {
  async loadFromManifest(manifest: PluginManifest): Promise<PluginInstance> {
    switch (manifest.entry.type) {
      case 'typescript': return this.loadTsPlugin(manifest);
      case 'mcp-server': return this.loadMcpPlugin(manifest);
      case 'wasm': return this.loadWasmPlugin(manifest);
      case 'binary': return this.loadBinaryPlugin(manifest);
    }
  }
}
```

### 功能收益

| 重构前 | 重构后 |
|--------|--------|
| 新能力需要同时改 TS 和 Rust | 插件开发者只需理解 PluginManifest 协议 |
| 无法热加载 | 插件可运行时 enable/disable |
| 无插件发现机制 | 统一注册表，Agent 可通过 ACP 查询可用插件 |
| Skill 和 Plugin 是两套概念 | 统一为 Plugin，降低学习成本 |

## 四、移动端方案统一（Flutter vs Tauri Mobile 二选一）

### 当前状态

```
acp_ui_flutter/        ← Flutter 项目，独立代码库，功能滞后
src-tauri/gen/android/ ← Tauri Android 构建产物（gitignored）
```

两套方案都在维护但 Flutter 明显滞后。核心问题：**同一份产品逻辑要写两遍**。

### 决策分析

| 维度 | Tauri Mobile | Flutter |
|------|-------------|---------|
| 代码复用 | 与桌面端共享 Rust 后端 + Vue 前端 | 完全独立代码 |
| 功能对齐 | 自动对齐（共用 src/） | 需要手动同步 |
| 性能 | WebView 渲染，接近原生 | 原生渲染 |
| 社区生态 | 较小，移动端仍在 beta | 成熟，大量插件 |
| 当前进度 | 有 gen/android 产物 | 项目骨架存在但不完整 |
| 维护成本 | 1 人可维护三端 | 需额外 Flutter 开发者 |

### 建议：选择 Tauri Mobile，暂停 Flutter

**理由**：
1. ACP-UI 的核心是 Web 技术栈（Vue 3），Tauri Mobile 的 WebView 方案天然复用
2. 项目已有 Android 构建产物（`src-tauri/gen/android/`）
3. 团队规模小（从代码提交历史看），双线作战不可持续

**迁移步骤**：
1. 将 Flutter 中已完成的功能列清单
2. 在 Tauri Mobile 中实现 Flutter 独有的功能（如有）
3. 将 `acp_ui_flutter/` 归档到 `_archive/`
4. 统一 Android/iOS 的构建 CI

### 功能收益

| 重构前 | 重构后 |
|--------|--------|
| 桌面版有功能 A，移动版没有 | 功能自动同步（共用 `src/`） |
| Bug 修两遍 | 修一遍 |
| 需要 Flutter + Rust + Vue 三种技能 | 只需 Rust + Vue |

## 五、路由分层与懒加载优化

### 当前状态

`router.ts` 中所有路由都是顶层平铺，无嵌套。`vite.config.ts` 的 `manualChunks` 手动指定了 8 个 chunk 分组。

### 重构方案

**嵌套路由 + 路由级代码分割**：

```typescript
const routes = [
  {
    path: '/chat',
    component: () => import('@/features/chat/ChatLayout.vue'),
    children: [
      { path: '', name: 'chat', component: () => import('@/features/chat/ChatView.vue') },
      { path: 'multi', name: 'multi-agent', component: () => import('@/features/chat/MultiAgentChat.vue') },
      { path: 'session/:id', name: 'session-detail', component: () => import('@/features/chat/ChatView.vue') },
    ]
  },
  {
    path: '/workflow',
    component: () => import('@/features/workflow/WorkflowLayout.vue'),
    children: [
      { path: '', name: 'workflow', component: () => import('@/features/workflow/WorkflowView.vue') },
      { path: 'editor/:id?', name: 'workflow-editor', component: () => import('@/features/workflow/WorkflowEditor.vue') },
    ]
  },
  // ...
]
```

### 功能收益

| 重构前 | 重构后 |
|--------|--------|
| 手动维护 vite manualChunks | 路由嵌套自动形成 chunk |
| 无法在功能模块内共享布局 | ChatLayout 提供统一的聊天页布局 |
| 新功能必须修改 router.ts | 功能模块可自描述路由（如 `features/workflow/routes.ts`） |

## 六、IDE Adapter 模块剥离

### 当前状态

```
src/lib/
├── android-studio-adapter.ts   ← 14KB
├── browser-adapter.ts           ← 16KB
├── hbuilderx-adapter.ts         ← 12KB
├── wechat-devtools-adapter.ts   ← 10KB
```

四个 IDE 适配器合计 ~52KB，但都是独立于 ACP 核心的功能。这些适配器的职责是"让 ACP Agent 能操作 IDE"——按 Plugin 架构理念，每个 IDE 适配器应是一个独立插件。

### 重构方案

将四个 adapter 分别转为 Plugin，通过统一的 `PluginManifest` 注册：

```
src/lib/adapters/               ← 新位置
├── index.ts                    ← AdapterRegistry
├── android-studio/
│   ├── manifest.json           ← PluginManifest
│   └── adapter.ts
├── browser/
│   ├── manifest.json
│   └── adapter.ts
├── hbuilderx/
│   ├── manifest.json
│   └── adapter.ts
└── wechat-devtools/
    ├── manifest.json
    └── adapter.ts
```

### 功能收益

| 重构前 | 重构后 |
|--------|--------|
| 所有 adapter 随主包加载 | 按需加载（用户只用 Android Studio，就不加载微信开发者工具 adapter） |
| 新增 IDE 支持需改核心代码 | 新增 adapter = 新增一个插件目录 + manifest |
| IDE adapter 与核心耦合 | 通过 Plugin Protocol 解耦 |

## 八、测试体系重构

### 当前状态

- 5 个单元测试文件（全在 `src/lib/agent-runtime/__tests__/` 和 `src/stores/__tests__/`）
- 15 个 E2E 测试（需手动启动 dev server）
- Rust 端零测试

### 重构方案

**测试金字塔重建**：

```
E2E (15 个 → 保持，加自动启动)
  ↑
集成测试 (新增 10-15 个: Store + Transport + ACP Bridge)
  ↑
单元测试 (5 → 30+ 个: 每个 lib 模块至少 1 个测试文件)
```

**关键模块必须覆盖**：

| 模块 | 优先级 | 原因 |
|------|--------|------|
| `WebSocketTransport` | P0 | 所有远程 Agent 依赖它，已有注入接口但缺测试 |
| `AcpClientBridge` | P0 | JSON-RPC 路由核心 |
| `ContextCompactor` | P1 | 直接影响 token 用量和对话质量 |
| `TokenOptimizer` | P1 | 直接影响成本 |
| `SecretsSanitizer` | P1 | 安全相关 |
| `permission_checker.rs` | P1 | 安全相关 |
| `circuit_breaker.rs` | P2 | 稳定性关键 |

**Rust 测试框架引入**：
- 使用 Rust 内置 `#[cfg(test)]` + `#[test]`
- 数据库模块 (`database.rs` 47KB) 已有复杂逻辑，必须测试

### 功能收益

| 重构前 | 重构后 |
|--------|--------|
| 修改核心模块不知道有没有破坏功能 | CI 自动跑相关测试 |
| 重构不敢动 Rust 代码 | 有测试保护 |
| Bug 修了可能复发 | 回归测试防止 |
