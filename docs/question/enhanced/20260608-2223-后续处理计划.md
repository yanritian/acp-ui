## 三、后续行动计划（按优先级排序）

### P0：必须立即处理（阻碍编译或严重功能缺陷）

#### 3.1 修复 Flutter instruction_screen.dart 编译错误

`_InstructionTextField` 的 `initState()`/`dispose()` 重复定义，直接导致 Flutter 编译失败。

**工作量**：10 分钟

#### 3.2 修复 AgentConfigView setInterval 内存泄漏

`onMounted` 中创建的 2 秒轮询定时器未在 `onUnmounted` 中清除，页面反复进出会累积定时器。

**工作量**：5 分钟

#### 3.3 处理 bot_gateway.rs 孤儿代码

三个选项：
- **A（推荐）**：删除整个文件。现有 `bot_adapters.rs` 已在使用且已注册，bot_gateway.rs 是重复造轮子
- **B**：注册到 `lib.rs` 并补全 stub 适配器，但工作量巨大且与 bot_adapters.rs 冲突
- **C**：归档到 `_archive/`

**工作量**：A=5分钟，B=2-3天，C=5分钟

#### 3.4 处理 hermes_traits.rs 死代码

三个选项：
- **A（推荐）**：暂时移除 `mod hermes_traits;` 声明，避免编译无用代码
- **B**：接入 hermes_flow 模块，实现真实的 trait 调用
- **C**：保留但标注 `#[cfg(feature = "experimental")]`

**工作量**：A=2分钟，B=1-2天

### P1：高优先级（假数据问题 — DeepSeek 核心质疑）

#### 3.5 解决 HermesDashboard/EnhancedHermesDashboard 假数据

需要先审查这两个组件的数据源。如果确实是全假数据：
- **选项 A（推荐短期）**：从导航中移除或标注 "(演示)" 标签
- **选项 B（中期）**：接入真实的 agent_orchestration 后端数据

**工作量**：A=15分钟，B=1-2天

#### 3.6 解决 TaskGraphView 假数据

router.ts 中 `createMockTaskDag()` 直接作为 props 传入。应该：
- 短期：从导航移除或标注 "(演示)"
- 中期：接入真实的任务执行 DAG 数据

**工作量**：短期=15分钟，中期=1天

#### 3.7 前端接入 orchestration/approval/sync 的 23 个 Tauri 命令

这是 GLM5 最大的遗留问题——后端做了大量工作但前端完全不调用。需要：
1. 在 `src/lib/host/` 中添加 invokeOrProxy 封装
2. 创建对应的 Pinia store 或 composable
3. 在相关 Vue 组件中调用

**按模块拆分**：
- `orchestration_*` 12 个命令 → AgentTeamsDashboard / DashboardView 接入
- `approval_*` 4 个命令 → PermissionDialog 改为非阻塞通知，接入审批流程
- `sync_*` 7 个命令 → 消息持久化、会话状态同步

**工作量**：2-3天

#### 3.8 TokenOptimizerPanel 数据验证

审查 `token-optimizer.ts` 的 `getCacheStats()` 数据链路，确认是否与真实 agent 调用打通。如未打通，标注 "(演示)" 或接入真实数据。

**工作量**：0.5天

#### 3.9 StatusView/MonitorView 空壳处理

两个页面几乎没有数据。选项：

**工作量**：30分钟

**做得好的**：
- Rust 后端模块质量较高（agent_orchestration、approval_engine、sync_engine 都是真实实现）
- TypeScript 工具库质量好（acp-protocol、workflow-dsl、push-service）

**核心问题**：

- **"死代码堆积"**：bot_gateway.rs（1245行）和 hermes_traits.rs（633行）共 1878 行无用代码

这些问题是下一步工作的重点。
