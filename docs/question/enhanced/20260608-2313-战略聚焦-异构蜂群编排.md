# ACP-UI 战略聚焦：异构 Agent 蜂群编排

> 核心判断：顶层蜂群是 Agent 基础设施的终局形态，ACP-UI 要做 Agent 世界的 Kubernetes。
> 日期: 2026-06-08

---

## 一、战略判断

### 为什么是蜂群

当前 Agent 格局正在重演云计算的历史。Codex、Claude Code、Copilot、Gemini CLI 是今天的"虚拟机"——每一个都很强，但都是独立运行的单体。它们各自能启动 subagent，但那只是虚拟机里的多线程，不是真正的分布式协调。

Anthropic 的 Dynamic Workflows / Ultracode 本质上就是"让 Claude Code 当蜂群 Queen，启动一堆 Worker"。但它是闭源蜂群——只能用 Claude，不能调 Codex，不能调 Gemini。

**ACP-UI 的差异化机会：开源异构蜂群。** 任何 Agent 都能加入，由 ACP 协议来编排。Codex 做代码生成、Claude Code 做代码理解和重构、Gemini 做多模态——它们各自是某个维度的专家，但没有人能把它们组成一个团队。

### 权力转移

当 Codex 自己启动 subagent 时，Codex 是老板。当 ACP-UI 把 Codex 注册为蜂群的一个 Worker 时，控制权在蜂群编排者手里。这意味着：

**蜂群编排者的价值 > 任何一个 Agent 的价值**

就像 K8s 的价值 > 任何一台虚拟机。虚拟机变成商品（利润越来越薄），而 K8s 成了基础设施标准。

### 一句话定义

**ACP-UI 不是 Agent 客户端，是 Agent 蜂群的操作系统。ACP 是蜂群的通信协议，UI 是蜂群的控制面板。**

## 二、所有能力服务于蜂群

| 能力 | 为蜂群解决什么问题 |
|------|------------------|
| ACP 协议层 | 蜂群的通信基础——Agent 间如何发现、协商、通信 |
| 可插拔架构 | 新 Agent 通过 Plugin Manifest 加入蜂群——扩展性 |
| Token 优化 | 蜂群跑起来之后省钱——KV Cache + 模型路由 |
| 自进化 | 蜂群执行任务过程中自动沉淀 Skill——越用越强 |
| 自修复 | 蜂群中某个 Worker 挂了自动替补——容错性 |
| IM 通道 | 蜂群跑完任务通知你、远程审批——控制面板 |
| CLI | 命令行直接操控蜂群——高级用户界面 |
| 向量记忆 | 蜂群所有 Worker 共享知识——HNSW 跨 Agent 记忆 |
| Dynamic Workflows | 蜂群的任务编排脚本——百级并行 |

**判断标准：如果一个功能不能让蜂群更好用，就先不做。**

## 三、蜂群编排的核心难题（GLM5 必须理解）

### 3.1 异构 Agent 的状态管理（最难的部分）

Codex 正在执行任务 A，执行到一半报错了。Claude Code 在做任务 B，还没做完。Gemini 在等前两个的结果才能开始。

- Codex 重试还是换 Agent？
- Claude Code 超时了怎么办？
- Gemini 的输入依赖前两者的输出，但格式不一致怎么转换？
- 三个 Agent 的上下文窗口都快满了，怎么压缩？

这是蜂群编排的硬骨头。Ruflo 用 Adaptive Queen 解决了一部分（Queen 失败时自动选举新 Queen），但它只支持 Claude 生态。异构蜂群在技术上更难，因为每个 Agent 的输入输出格式、错误处理、能力声明都不一样。

### 3.2 能力声明与任务匹配

每个 Worker Agent 需要声明自己擅长什么：

```
Codex:     { 擅长: [代码生成, 重构, 测试], 不擅长: [文档, 多模态], 并发: 1, 平均延迟: 30s }
Claude Code: { 擅长: [代码理解, 重构, 文档], 不擅长: [并发执行], 并发: 1, 平均延迟: 45s }
Gemini:    { 擅长: [多模态, 搜索, 长上下文], 不擅长: [精确代码生成], 并发: 3, 平均延迟: 20s }
```

Leader Agent（或编排引擎）根据任务描述，自动选择最合适的 Worker 组合。smart_router.rs 的三层复杂度评估可以复用，但需要扩展为 Agent 能力匹配。

### 3.3 上下文隔离与共享

蜂群中每个 Worker 有独立的上下文窗口（避免上下文爆炸），但它们需要共享关键信息：

- **私有上下文**：每个 Worker 自己的对话历史、中间结果
- **共享上下文**：任务目标、已完成的子任务结果、全局约束
- **传递上下文**：Worker A 的输出 → Worker B 的输入，需要格式转换和摘要

这就是 HNSW 向量记忆的价值——所有 Worker 读写同一个向量库，实现跨 Agent 知识共享。

```rust
pub enum SwarmTopology {
    /// Star 拓扑：一个 Queen 分配任务给多个 Worker
    /// 
    ///         ┌─── Worker (Codex)
    /// Queen ──┼─── Worker (Claude Code)  
    ///         └─── Worker (Gemini)

    /// Chain 拓扑：流水线，前一个 Agent 的输出是后一个的输入
    /// 
    /// Codex(生成代码) → Claude Code(审查) → Gemini(写文档)
    Chain { workers: Vec<String> },
}
```

**Star 拓扑实现**：
```rust
impl SwarmOrchestrator {
    pub async fn execute_star(
        &self,
        task: &SwarmTask,
        queen_id: &str,
    ) -> Result<SwarmResult, SwarmError> {
        // 1. Queen 分析任务，拆分为子任务
        let queen = self.get_worker(queen_id)?;
        let decomposition = self.decompose_task(task, &queen).await?;
        
        // 2. 根据子任务类型匹配最佳 Worker
        let assignments = self.match_workers(&decomposition)?;
        
        // 3. 并行发送给 Workers
        let mut handles = Vec::new();
        for (worker_id, subtask) in &assignments {
            let handle = self.send_to_worker(worker_id, subtask).await?;
            handles.push((worker_id.clone(), handle));
        }
        
        // 4. 收集结果
        let results = self.collect_results(handles).await?;
        
        // 5. Queen 合并结果
        let final_result = self.merge_results(task, &results, &queen).await?;
        
        Ok(final_result)
    }
    
    /// 任务分解：让 Queen Agent 分析任务并拆分为子任务
    async fn decompose_task(
        &self,
        task: &SwarmTask,
        queen: &dyn SwarmAgentAdapter,
    ) -> Result<Vec<SubTask>, SwarmError> {
        let prompt = format!(
            "分析以下任务，拆分为可并行执行的子任务。每个子任务指定：\n\
             1. 描述\n\
             2. 需要的能力（code_gen/refactor/test/docs/review）\n\
             3. 依赖关系\n\n\
             任务：{}",
            task.description
        );
        let response = queen.send_task(&TaskDescription { prompt, ..Default::default() })?;
        // 解析响应为 Vec<SubTask>
        self.parse_decomposition(response)
    }
    
    /// Worker 匹配：根据子任务能力需求选择最佳 Worker
    fn match_workers(
        &self,
        subtasks: &[SubTask],
    ) -> Result<Vec<(String, SubTask)>, SwarmError> {
        let workers = self.get_idle_workers();
        let mut assignments = Vec::new();
        
        for subtask in subtasks {
            let best_worker = workers.iter()
                .filter(|w| w.status == WorkerStatus::Idle)
                .max_by_key(|w| {
                    // 计算能力匹配分数
                    w.capabilities.strengths.iter()
                        .filter(|s| subtask.required_capabilities.contains(s))
                        .count()
                })
                .ok_or(SwarmError::NoAvailableWorker)?;
            
            assignments.push((best_worker.id.clone(), subtask.clone()));
        }
        
        Ok(assignments)
    }
}
```

**Chain 拓扑实现**：
```rust
impl SwarmOrchestrator {
    pub async fn execute_chain(
        &self,
        task: &SwarmTask,
        worker_ids: &[String],
    ) -> Result<SwarmResult, SwarmError> {
        let mut current_input = task.description.clone();
        let mut stage_results = Vec::new();
        
        for (i, worker_id) in worker_ids.iter().enumerate() {
            let worker = self.get_worker(worker_id)?;
            
            let stage_prompt = format!(
                "你是流水线第 {}/{} 阶段。\n\
                 原始任务：{}\n\
                 上一阶段的输出：\n{}\n\n\
                 请基于以上输入完成你的阶段任务。",
                i + 1,
                worker_ids.len(),
                task.description,
                current_input
            );
            
            let result = worker.send_task(&TaskDescription {
                prompt: stage_prompt,
                ..Default::default()
            })?.wait().await?;
            
            stage_results.push(result.clone());
            current_input = result.output;  // 输出传给下一个 Worker
        }
        
        Ok(SwarmResult {
            final_output: current_input,
            stages: stage_results,
        })
    }
}
```

#### 2.2 错误处理与自动替补

```rust
/// Adaptive Queen 机制：Worker 失败时自动处理
impl SwarmOrchestrator {
    async fn handle_worker_failure(
        &self,
        failed_worker_id: &str,
        task: &SubTask,
    ) -> Result<TaskHandle, SwarmError> {
        // 1. 尝试重试（同一 Worker）
        let worker = self.get_worker(failed_worker_id)?;
        if worker.health_check() {
            // Worker 还活着，可能是临时错误，重试一次
            return self.send_to_worker(failed_worker_id, task).await;
        }
        
        // 2. Worker 不可用，找替代
        let replacement = self.find_replacement_worker(task)?;
        self.send_to_worker(&replacement.id, task).await
    }
    
    fn find_replacement_worker(
        &self,
        task: &SubTask,
    ) -> Result<SwarmWorker, SwarmError> {
        self.get_idle_workers()
            .into_iter()
            .filter(|w| {
                w.capabilities.strengths.iter()
                    .any(|s| task.required_capabilities.contains(s))
            })
            .max_by_key(|w| {
                // 优先选择负载低的 Worker
                100 - w.current_load_percent
            })
            .ok_or(SwarmError::NoAvailableWorker)
    }
}
```

#### 3.2 Pinia Store

新建 `src/stores/swarm.ts`：

```typescript
import { defineStore } from 'pinia';
import { ref, computed } from 'vue';
import {
  listWorkers, registerWorker, executeStar, executeChain,
  getTopology, healthCheck, cancelSwarmTask,
  type SwarmWorker, type SwarmTask, type SwarmResult, type WorkerStatus,
} from '@/lib/swarm-api';

export const useSwarmStore = defineStore('swarm', () => {
  const workers = ref<SwarmWorker[]>([]);
  const currentTask = ref<SwarmTask | null>(null);
  const taskResult = ref<SwarmResult | null>(null);
  const topology = ref<'star' | 'chain' | null>(null);
  const isLoading = ref(false);
  const error = ref<string | null>(null);
  let pollInterval: ReturnType<typeof setInterval> | null = null;

  const idleWorkers = computed(() => workers.value.filter(w => w.status === 'idle'));
  const busyWorkers = computed(() => workers.value.filter(w => w.status === 'busy'));
  const queenWorker = computed(() => workers.value.find(w => w.role === 'queen'));

  async function refreshWorkers() {
    try {
      workers.value = await listWorkers();
    } catch (e) {
      console.warn('[Swarm] Failed to refresh workers:', e);
    }
  }

  async function addWorker(agentType: string, name: string, config: Record<string, unknown> = {}) {
    const worker = await registerWorker(agentType, name, config);
    workers.value.push(worker);
    return worker;
  }

  async function runStarTask(description: string, queenId: string) {
    isLoading.value = true;
    error.value = null;
    currentTask.value = { description, created_at: Date.now() };
    
    try {
      startPolling();
      taskResult.value = await executeStar(currentTask.value!, queenId);
    } catch (e) {
      error.value = String(e);
    } finally {
      isLoading.value = false;
      stopPolling();
      await refreshWorkers();
    }
  }

  async function runChainTask(description: string, workerIds: string[]) {
    isLoading.value = true;
    error.value = null;
    currentTask.value = { description, created_at: Date.now() };
    
    try {
      startPolling();
      taskResult.value = await executeChain(currentTask.value!, workerIds);
    } catch (e) {
      error.value = String(e);
    } finally {
      isLoading.value = false;
      stopPolling();
      await refreshWorkers();
    }
  }

  function startPolling() {
    pollInterval = setInterval(async () => {
      await refreshWorkers();
    }, 2000);
  }

  function stopPolling() {
    if (pollInterval) {
      clearInterval(pollInterval);
      pollInterval = null;
    }
  }

  return {
    workers, currentTask, taskResult, topology, isLoading, error,
    idleWorkers, busyWorkers, queenWorker,
    refreshWorkers, addWorker, runStarTask, runChainTask,
  };
});
```

#### 3.3 SwarmDashboard 重写

修改 `src/features/plugins/SwarmDashboard.vue`，接入真实蜂群数据：

核心 UI 元素：
1. **Worker 注册区**：下拉选择 Agent 类型（Codex / Claude Code / 自定义），输入名称，一键注册
2. **拓扑选择器**：Star 或 Chain，可视化展示当前拓扑
3. **任务输入区**：输入任务描述，选择 Queen（Star）或 Worker 顺序（Chain），一键执行

## 八、分布式系统设计模式 —— 蜂群编排的底层思想

> **战略优先：不能用战术上的勤奋去掩盖战略上的懒惰。**

### 8.1 Elasticsearch 分片思想 → 任务分区与副本容错

**ES 核心机制**：索引被切分为多个 Shard，每个 Shard 有 Primary + Replica。写入走 Primary，读取可走 Replica。Primary 挂了，Replica 自动提升为 Primary。

**映射到蜂群**：

- **任务分区（Task Sharding）**：Queen 将一个大型任务（如"重构整个认证模块"）拆分为多个独立的 Task Shard（"重构登录组件"、"重构 Token 刷新逻辑"、"重构权限守卫"）。每个 Shard 分配给最合适的 Worker。
- **Primary/Replica Worker**：关键任务（如架构设计）分配 Primary Worker（Claude Code）+ Replica Worker（Codex）。Primary 执行，Replica 待命。Primary 超时或崩溃，Replica 接管，避免单点失败。
- **Shard 再平衡（Rebalance）**：当新 Worker 加入蜂群（比如启动了一个 Gemini Worker），Queen 可以将排队中的 Task Shard 重新分配，实现负载均衡。

```rust
// 任务分区结构
pub struct TaskShard {
    pub id: String,
    pub parent_task: String,
    pub payload: TaskPayload,
    pub primary_worker: WorkerId,
    pub replica_worker: Option<WorkerId>,  // 关键任务有副本
    pub status: ShardStatus,  // Pending | Assigned | Running | Completed | Failed | Reassigned
    pub timeout_ms: u64,
}

pub enum ShardStatus {
    Pending,
    Assigned,
    Running,
    Completed,
    Failed { reason: String, reassigned_to: Option<WorkerId> },
    Reassigned,  // Primary 失败后已切换到 Replica
}
```

**Phase 2 实现要点**：在 Topology Engine 中实现 `TaskPartitioner`，将复杂任务拆解为 TaskShard 列表；在 Star 拓扑的 `execute_parallel` 中加入 Replica 逻辑——Primary Worker 超过 `timeout_ms` 未返回，自动将同一 Shard 发给 Replica。

### 8.2 Redis Cluster 哈希槽 → 能力路由与去中心化分发

**Redis Cluster 核心机制**：16384 个 Hash Slot，每个 Key 通过 CRC16 映射到 Slot，Slot 分配给具体节点。新增节点时，Slot 迁移实现去中心化扩展。

**映射到蜂群**：

- **能力槽位（Capability Slots）**：不用 16384 个槽，而是根据 Worker 声明的能力定义槽位。例如：`frontend`、`backend`、`testing`、`architecture`、`documentation`、`debugging`。每个 Task 通过其类型映射到对应槽位，槽位路由到最擅长的 Worker。
- **一致性哈希路由**：当蜂群有多个同类型 Worker（比如 2 个 Codex 实例），任务通过一致性哈希分配到不同实例，避免所有任务打到同一个 Worker。
- **槽位迁移（Slot Migration）**：当新 Worker 加入时（比如注册了一个擅长 testing 的 Gemini Worker），相关能力槽位从现有 Worker 迁移过来，实现动态负载均衡。

### 8.3 ZooKeeper 租约选举 → 防脑裂与 Queen 高可用

**ZK 核心机制**：基于临时节点 + 顺序号实现 Leader Election。Leader 持有 30 秒租约，每 10 秒续约。租约过期，其他节点自动发起新一轮选举。防止"两个 Leader 同时写数据"的脑裂问题。

**映射到蜂群**：

- **Queen 租约机制**：当前 Star 拓扑中 Queen 是静态指定的（用户选择或默认第一个 Worker）。引入租约后，Queen 每 10 秒向 Orchestrator 续约。Queen 崩溃或卡死（比如 Claude Code 进程无响应），租约 30 秒后过期，Orchestrator 自动将剩余 Worker 中能力最强的提升为新 Queen。
- **防脑裂**：在 Chain 拓扑中，如果 Chain 的中间节点（Worker B）同时收到来自两个 Queen 的指令（旧 Queen 网络延迟恢复 + 新 Queen 已选举），Worker 只接受租约有效的 Queen 的指令。无效 Queen 的指令直接丢弃。
- **Adaptive Queen 升级**：当任务复杂度超出当前 Queen 的能力范围（比如 Queen 是 Codex，但任务需要长上下文推理），Orchestrator 可以主动发起 Queen 切换——将 Claude Code 提升为 Queen，Codex 降级为 Worker。

```rust
// Queen 租约
pub struct QueenLease {
    pub queen_id: WorkerId,
    pub granted_at: Instant,
    pub ttl_seconds: u64,        // 默认 30 秒
    pub renew_interval: u64,     // 每 10 秒续约
}

impl QueenLease {
    pub fn is_valid(&self) -> bool {
        self.granted_at.elapsed().as_secs() < self.ttl_seconds
    }

    pub fn renew(&mut self) {
        self.granted_at = Instant::now();
    }
}

// 防脑裂：Worker 端验证
impl WorkerNode {
    pub fn accept_task(&self, from_queen: WorkerId, task: TaskShard) -> Result<(), SwarmError> {
        if let Some(lease) = &self.current_queen_lease {
            if lease.queen_id != from_queen || !lease.is_valid() {
                return Err(SwarmError::SplitBrain {
                    expected_queen: lease.queen_id.clone(),
                    received_from: from_queen,
                });
            }
        }
        // 接受任务...
        Ok(())
    }
}
```

**Phase 2 实现要点**：在 `SwarmOrchestrator` 中增加 `QueenLease` 管理器。Star 拓扑执行前，先获取 Queen 租约；执行过程中 Queen 定期续约；Queen 失败时自动触发 `elect_new_queen()`——按 Worker 能力声明排序，选择最合适的继任者。这是蜂群从"玩具"走向"生产级"的核心差异。

### 8.4 本地 + 云混合架构 → 成本与弹性的平衡

**核心思想**：本地 Agent（Codex CLI、Claude Code CLI 通过 stdio 调用）是"固定成本为零的常备军"；云端 Agent（API 端点，如 Claude API、OpenAI API、Gemini API）是"按需付费的雇佣兵"。两者混合使用，才能在成本和弹性之间取得平衡。

**架构分层**：

```
┌─────────────────────────────────────────────────────┐
│                   ACP-UI Orchestrator                │
│              (Queen 选举 / 任务路由 / 状态管理)        │
├──────────────────────┬──────────────────────────────┤
│    本地 Worker 层     │        云端 Worker 层         │
│  ┌────────────────┐  │  ┌─────────────────────────┐ │
│  │ Codex CLI      │  │  │ Claude API Worker       │ │
│  │ (stdio, 零成本) │  │  │ (HTTP, 按需付费)         │ │
│  ├────────────────┤  │  ├─────────────────────────┤ │
│  │ Claude Code CLI│  │  │ OpenAI API Worker       │ │
│  │ (stdio, 零成本) │  │  │ (HTTP, 按需付费)         │ │
│  ├────────────────┤  │  ├─────────────────────────┤ │
│  │ 自定义 CLI     │  │  │ Gemini API Worker       │ │
│  │ (stdio, 零成本) │  │  │ (HTTP, 按需付费)         │ │
│  └────────────────┘  │  └─────────────────────────┘ │
│   特点：              │   特点：                      │
│   - 零边际成本        │   - 弹性扩缩                  │
│   - 数据不出本机      │   - 可并发 N 个实例            │
│   - 受限于本地资源    │   - 适合突发大任务             │
└──────────────────────┴──────────────────────────────┘
```

**混合调度策略**：

1. **隐私优先**：涉及用户代码、敏感数据的任务，**只分配给本地 Worker**。云端 Worker 不得接触。
2. **本地优先，云端溢出**：正常情况下优先使用本地 Worker（零成本）。当本地 Worker 全部忙碌且任务队列积压超过阈值时，自动将非敏感任务溢出到云端 Worker。
3. **云端特种部队**：某些任务明确需要云端能力（比如需要 Claude Opus 的长上下文窗口、需要 Gemini 的多模态能力），直接路由到对应的云端 Worker，不走本地。
4. **成本预算**：用户可以在设置中配置"云端预算上限"（如每月 $50）。Orchestrator 在溢出到云端前检查预算，超出则任务排队等待本地 Worker 释放。

```rust
pub enum WorkerLocation {
    Local { command: String, args: Vec<String> },     // stdio 通信
    Cloud { endpoint: String, api_key_env: String },  // HTTP 通信
}

pub struct HybridScheduler {
    local_workers: Vec<WorkerNode>,
    cloud_workers: Vec<WorkerNode>,
    cloud_budget_cents: u64,   // 云端预算（美分）
    spent_cents: u64,          // 已消耗
    overflow_threshold: usize, // 本地队列积压多少任务时开始溢出
}

impl HybridScheduler {
    pub fn schedule(&mut self, task: TaskPayload) -> ScheduleDecision {
        // 1. 敏感任务：只走本地
        if task.is_sensitive {
            return self.schedule_local(task);
        }

        // 2. 需要特殊能力：直接走云端
        if task.requires_cloud_capability() {
            return self.schedule_cloud(task);
        }

        // 3. 本地有空闲 Worker：走本地
        if let Some(worker) = self.local_workers.iter().find(|w| w.is_idle()) {
            return self.schedule_local(task);
        }

        // 4. 本地全忙 + 队列积压 > 阈值 + 预算充足：溢出到云端
        if self.pending_queue.len() > self.overflow_threshold
            && self.spent_cents + task.estimated_cost() < self.cloud_budget_cents
        {
            return self.schedule_cloud(task);
        }

        // 5. 否则：排队等本地 Worker
        self.pending_queue.push_back(task);
        ScheduleDecision::Queued
    }
}
```

**Phase 1-2 实现要点**：Phase 1 的 `SwarmAgentAdapter` 已经区分了 `LocalAdapter`（stdio）和未来的 `CloudAdapter`（HTTP）。Phase 2 在 `SwarmOrchestrator` 中引入 `HybridScheduler`，先只实现"本地优先"逻辑（Phase 1-2 不需要真的接云端 API），但预留 `CloudAdapter` trait 和预算检查接口。Phase 4 Demo 时，可以用 `echo` 命令模拟本地 Worker 和云端 Worker 的差异（本地 Worker 延迟 500ms，云端 Worker 延迟 200ms 但标记为"cost: $0.01"）。

### 8.6 战略视角：为什么这些模式决定了 ACP-UI 的上限

回到最核心的判断：**ACP-UI 的价值不在于它是一个"更好的 AI 客户端"，而在于它是一个 Agent 编排层——Agent 的 Kubernetes。**

Kubernetes 之所以成为容器编排的事实标准，不是因为它能启动容器（Docker 也能），而是因为它解决了：调度（哪个容器跑在哪个节点）、容错（节点挂了自动迁移）、扩缩（流量大了自动加节点）、网络（容器间怎么通信）。

ACP-UI 的蜂群编排，要解决的是一模一样的问题，只不过对象从容器变成了 Agent：

- **调度** → ES 分片 + Redis 哈希槽：哪个 Agent 执行哪个任务
- **容错** → ZK 租约 + Primary/Replica：Agent 挂了怎么办
- **扩缩** → 本地+云混合：任务多了怎么加 Agent，成本怎么控制
- **网络** → ACP 协议：Agent 之间怎么通信，状态怎么同步

如果 Phase 1-4 能把这四个问题的**最简版本**跑通，ACP-UI 就不再是一个"有潜力的项目"，而是一个**真正有技术壁垒的编排系统**。

这就是为什么不能用战术上的勤奋去掩盖战略上的懒惰。写一百个 Vue 组件不如把 Queen 租约选举做对。修十个 UI bug 不如让任务分片 + 副本容错跑通一次。

**GLM5 执行 Phase 1-4 时，每一步都要问自己：这个改动是在加固编排层的地基，还是在给外墙刷漆？**

## 九、Goal 驱动执行模型 —— 蜂群编排的正确抽象层

> **参考来源**: Codex CLI `/goal` 命令（v0.128.0 首发）、Claude Code `/goal` 命令（v2.1.139 跟进）
> **核心思想**: 不要给 Agent 分配"任务"，要给 Agent 设定"目标"。任务有固定的执行步骤，目标有明确的完成条件。

### 9.1 为什么 TaskShard 应该升级为 GoalShard

之前的设计中，Queen 把任务拆成 TaskShard 分配给 Worker。问题是：Worker "执行完了"不等于"做对了"。TaskShard 只有状态（Running/Completed/Failed），没有**完成条件的客观验证**。

`/goal` 的核心洞见是：**执行器和评估器必须分离**。干活的 Worker 不能自己说"我做完了"，必须由独立的评估器验证完成条件是否满足。

这和分布式系统的 Reconcile Loop（如 K8s 的控制器）是同构的：你声明期望状态（desired state），执行者不断循环直到实际状态收敛到期望状态。

### 9.2 Goal 数据结构

```rust
/// Goal —— 蜂群编排的核心抽象
/// 替代之前的 TaskShard，每个 Goal 有明确的完成条件和评估方式
pub struct Goal {
    pub id: String,
    pub description: String,          // 人类可读的目标描述
    
    /// 完成条件 —— 什么算"做完了"
    pub completion_condition: CompletionCondition,
    
    /// 评估器 —— 谁来验证完成条件
    pub evaluator: GoalEvaluator,
    
    /// 执行者 —— 谁来干活
    pub executor: WorkerId,
    
    /// 依赖 —— 哪些 sub-goal 必须先收敛
    pub depends_on: Vec<String>,
    
    /// Token 预算
    pub token_budget: u64,
    pub tokens_used: u64,
    
    /// 最大迭代轮数（防止无限循环）
    pub max_iterations: u32,
    pub current_iteration: u32,
    
    /// 状态
    pub status: GoalStatus,
}

/// 完成条件 —— 客观可验证
pub enum CompletionCondition {
    /// 命令退出码为 0
    CommandSuccess { command: String, args: Vec<String> },
    /// 输出包含特定文本
    OutputContains { command: String, pattern: String },
    /// 输出匹配正则
    OutputMatches { command: String, regex: String },
    /// 多个条件全部满足
    All(Vec<CompletionCondition>),
    /// 多个条件满足任意一个
    Any(Vec<CompletionCondition>),
    /// 文件存在且内容匹配
    FileCheck { path: String, content_pattern: Option<String> },
    /// 自定义评估函数（Queen 判断）
    QueenJudgment { criteria: String },
}

/// 评估器类型
pub enum GoalEvaluator {
    /// Queen 作为评估器（默认）
    Queen,
    /// 自动化评估（运行 completion_condition 中的命令）
    Auto,
    /// 指定另一个 Worker 做评估（对抗性审查）
    Adversarial(WorkerId),
}

pub enum GoalStatus {
    Pending,          // 等待依赖完成
    Active,           // 正在执行
    Evaluating,       // 正在评估是否达成
    Converged,        // 目标达成 ✓
    Iterating,        // 未达成，继续迭代
    BudgetExhausted,  // Token 预算耗尽
    MaxIterReached,   // 达到最大迭代轮数
    Failed(String),   // 执行失败
}
```

### 9.3 Goal 执行循环（Reconcile Loop）

```
                    ┌─────────────────────────┐
                    │   Goal: 所有测试通过     │
                    │   完成条件: npm test = 0  │
                    └───────────┬─────────────┘
                                │
                    ┌───────────▼─────────────┐
                    │  Worker 执行（Executor）  │
                    │  写代码、改代码、修 bug   │
                    └───────────┬─────────────┘
                                │
                    ┌───────────▼─────────────┐
                    │  Queen 评估（Evaluator） │
                    │  运行 npm test           │
                    │  检查退出码 == 0？        │
                    └─────┬──────────────┬────┘
                          │              │
                     不满足            满足
                          │              │
                    ┌─────▼─────┐  ┌─────▼─────┐
                    │ 继续迭代   │  │ Converged  │
                    │ 带错误信息  │  │ 目标达成 ✓ │
                    │ 重新执行   │  └───────────┘
                    └───────────┘
```

```rust
impl SwarmOrchestrator {
    /// Goal 执行循环 —— 蜂群编排的核心算法
    pub async fn execute_goal(&self, goal: &mut Goal) -> GoalResult {
        loop {
            // 1. 检查预算
            if goal.tokens_used >= goal.token_budget {
                goal.status = GoalStatus::BudgetExhausted;
                return GoalResult::Exhausted { tokens_used: goal.tokens_used };
            }
            
            // 2. 检查最大迭代
            if goal.current_iteration >= goal.max_iterations {
                goal.status = GoalStatus::MaxIterReached;
                return GoalResult::MaxIterReached { iterations: goal.current_iteration };
            }
            
            // 3. Worker 执行
            goal.status = GoalStatus::Active;
            let execution = self.dispatch_to_worker(
                &goal.executor,
                &goal.description,
                goal.current_iteration,  // 第 N 轮迭代
            ).await?;
            
            goal.tokens_used += execution.tokens_used;
            
            // 4. 评估完成条件
            goal.status = GoalStatus::Evaluating;
            let evaluation = self.evaluate_completion(goal, &execution).await;
            
            if evaluation.converged {
                goal.status = GoalStatus::Converged;
                return GoalResult::Success {
                    iterations: goal.current_iteration + 1,
                    tokens_used: goal.tokens_used,
                };
            }
            
            // 5. 未收敛 → 带着错误信息继续迭代
            goal.current_iteration += 1;
            goal.status = GoalStatus::Iterating;
            // 将评估结果（哪些条件不满足）追加到 goal 描述中
            // Worker 下一轮能看到"上一轮为什么没过"
            goal.description = format!(
                "{}\n\n[Iteration {} feedback]: {}",
                goal.description, goal.current_iteration, evaluation.feedback
            );
        }
    }
}
```

### 9.4 蜂群级别的 Goal 编排

**Star 拓扑 = Goal 并行扇出 + 收敛检查**

```
顶层 Goal: "React 登录模块完成"
  完成条件: All(npm test == 0, vue-tsc --noEmit == 0, storybook build == 0)
  │
  ├── Sub-Goal A → Worker: Claude Code
  │   条件: npm test -- --grep "login" == 0
  │   评估: Auto（运行测试命令）
  │
  ├── Sub-Goal B → Worker: Codex
  │   条件: vue-tsc --noEmit == 0
  │   评估: Auto（运行编译命令）
  │   depends_on: [A]  ← B 的代码依赖 A 的组件
  │
  └── Sub-Goal C → Worker: Gemini
      条件: storybook build == 0
      评估: Auto（运行构建命令）
      depends_on: [A]
```

Queen 的执行逻辑：
1. Sub-Goal A 无依赖，立即启动
2. A 收敛后，B 和 C 并行启动
3. B 和 C 都收敛后，Queen 评估顶层 Goal 的所有条件
4. 全部满足 → 蜂群任务成功

**Chain 拓扑 = Goal 依赖链 + 逐步收敛**

```
Goal 1: 需求文档通过评审 → Queen 评估
  ↓ (converged)
Goal 2: 架构设计无循环依赖 → Auto（运行 depcheck）
  ↓ (converged)
Goal 3: 代码实现编译通过 → Auto（cargo check）
  ↓ (converged)
Goal 4: 所有测试通过 → Auto（cargo test）
  ↓ (converged)
Goal 5: 文档自动生成成功 → Auto（cargo doc）
```

每个 Goal 的 Worker 可以看到前一个 Goal 的产出物（通过共享的 workspace），但必须等前一个 Goal 状态为 Converged 才能开始。

### 9.5 Goal 与之前设计的关系

| 之前的概念 | 升级为 | 变化 |
|-----------|--------|------|
| TaskShard | **Goal** | 从"执行步骤"变为"完成条件" |
| ShardStatus (Running/Completed/Failed) | **GoalStatus** (Active/Evaluating/Converged/Iterating) | 新增评估和迭代状态 |
| Queen 合并结果 | **Queen 评估收敛** | Queen 从"结果合并器"变为"目标评估器" |
| Star 并行执行 | **Goal 并行扇出 + 收敛检查** | 并行执行 + 自动验证 |
| Chain 流水线 | **Goal 依赖链 + 逐步收敛** | 从"输出传递"变为"目标达成后触发下一环" |
| timeout_ms | **token_budget + max_iterations** | 从"超时"变为"预算+轮数"双重保护 |

### 9.6 这对 acp-swarm 意味着什么

Goal 驱动模型让 acp-swarm 的定位从"任务分发器"升级为"目标收敛引擎"。这不只是语义上的差别：

1. **可验证性**: 每个 Goal 的完成条件都是客观可执行的命令（`npm test`、`cargo check`），不是主观判断。这意味着蜂群任务的成功/失败是可以程序化验证的。

2. **自适应**: Worker 第一轮没通过测试，Queen 把测试失败信息反馈给 Worker，Worker 下一轮自动修复。不需要人类介入。这就是 `/goal` 的核心价值——agent 自己迭代到目标达成。

3. **组合性**: Goal 可以嵌套（顶层 Goal 包含 Sub-Goal）、可以链式依赖（B depends_on A）、可以并行扇出。Star 和 Chain 拓扑不再是两种独立的执行模式，而是 Goal 依赖图的两种特例。

4. **与测试工程的天然整合**: Phase E（测试工程）中的稳定性测试，本质上就是一组 Goal："100 次任务全过"、"内存增长 < 50%"、"Queen 故障后 30 秒内切换"。蜂群编排自身的质量保证也用 Goal 驱动。

**GLM5 在 Phase 3 实现蜂群原型时，核心数据结构就是 Goal，不是 TaskShard。Worker 执行的不是一轮任务，而是 Goal 的 Reconcile Loop。Queen 做的不是结果合并，而是完成条件评估。**
