## P0 — 严重问题 (4项)

### 1. goal_graph.rs — remove_goal() 逻辑 BUG
**文件**: `src-tauri/src/goal_graph.rs:261-287`
**问题**: 先调用 `self.dependencies.remove(id)` 删除了依赖记录，然后再用 `self.dependencies.get(id)` 试图读取已删除的条目，导致反向依赖映射永远不会被清理，造成数据泄漏和潜在的死锁风险。
**修复**: 使用 `self.dependencies.remove(id).unwrap_or_default()` 一次性取出依赖列表并保存为局部变量，随后遍历清理反向引用。

### 2. goal_evaluator.rs — 命令注入风险
**文件**: `src-tauri/src/goal_evaluator.rs:69-116`
**问题**: `eval_command()` 直接将用户提供的命令字符串传给 `sh -c`，无任何过滤或限制，存在命令注入风险。
**修复**: 添加危险命令拒绝列表（denylist），包含 `rm -rf /`、`mkfs`、`dd if=`、`wget`、`curl`、`nc`、`bash -i` 等危险命令模式；同时添加 512 字符的命令长度上限。被拒绝的命令返回明确的错误信息。

### 3. client.ts — WebSocket onclose 未 reject pending requests
**文件**: `src/lib/acp-protocol/client.ts:76-86`
**问题**: WebSocket 断开连接时，`pendingRequests` Map 中的 Promise 永远得不到 resolve 或 reject，造成 Promise 泄漏和内存泄漏。
**修复**: 在 `onclose` 回调中遍历所有 pending requests，以 `Error('WebSocket connection closed')` reject 每一个，然后清空 Map。

### 4. swarm_orchestrator.rs — execute_chain() 假数据
**文件**: `src-tauri/src/swarm_orchestrator.rs:886-912`
**问题**: `execute_chain()` 返回伪造的成功输出（`success: true`），实际上并未调用任何真实的 worker adapter，前端会误认为任务已成功完成。
**修复**: 将 `success` 改为 `false`，在 `error` 字段中明确标注 "Legacy execute_chain does not dispatch to real adapters; use topology::execute_chain for production execution"，引导使用新的 topology 模块。

## P1 — 高优先级 (4项)

### 5. remote-control/server.ts — 8 个 handler 返回假数据
**文件**: `src/lib/remote-control/server.ts:146-217`
**问题**: `startAgent`、`stopAgent`、`sendMessageToAgent`、`handleApprove`、`handleReject`、`getStatus`、`pauseAgent`、`resumeAgent` 全部返回硬编码的假数据，调用者无法区分真实响应和假数据。
**修复**: 所有 8 个 handler 改为抛出 `Error('not implemented — wire to ...')`，并在 `executeCommand` 外层添加 try/catch 统一处理错误，返回 `{ error: message }` 格式。

### 6. reconcile.rs — 同步阻塞异步执行器
**文件**: `src-tauri/src/reconcile.rs:173`
**问题**: 在轮询循环中使用 `std::thread::sleep()` 阻塞当前线程，如果从 async 上下文调用会阻塞 tokio executor。
**修复**: 添加详细文档注释，说明当前行为及 Phase 3 的 async 重构计划。当前代码在 Tauri 同步命令的线程池中运行，不会直接阻塞 tokio runtime，但建议在 Phase 3 中全面转为 async。

### 7. queen_lease.rs — 双锁死锁风险
**文件**: `src-tauri/src/queen_lease.rs:280-297`
**问题**: `gather_candidates()` 同时持有 `self.workers` 和 `self.worker_health` 两个 Mutex 的锁，如果其他线程以不同顺序获取这两个锁，会造成死锁。
**修复**: 先克隆 `workers` 数据到局部变量并释放锁，再克隆 `worker_health` 数据到局部变量并释放锁，最后在局部数据上进行遍历计算，避免同时持有两个锁。

### 8. channel-registry.ts — 审批回复硬编码飞书
**文件**: `src/lib/im-channels/channel-registry.ts:168-180`
**问题**: `approve` 和 `reject` 命令的回复消息固定发送到 `'feishu'` 渠道，无论原始请求来自哪个渠道（钉钉、微信、Telegram 等）。
**修复**: 从 `command.payload.channel` 中提取原始渠道类型，回发到对应渠道；如未指定则默认 fallback 到 `'feishu'`。同时添加块级作用域 `{}` 避免 switch case 中的变量声明冲突。

## P2 — 中等优先级 (4项)

### 9. capability-evolver.ts — 未使用导入 + 负值评分
**文件**: `src/lib/self-improvement/capability-evolver.ts`
**问题**:
- 第 7 行导入了 `useOrchestrationStore` 但从未使用
- 第 265 行 `(1 - score.avgDuration / 10000)` 当 `avgDuration > 10000` 时会产生负值，导致 `compositeScore` 可能为负

**修复**:
- 删除未使用的 `useOrchestrationStore` 导入
- 用 `Math.max(0, 1 - score.avgDuration / 10000)` 将 duration 分量限制在 [0, 1] 范围
- 最终总分也用 `Math.max(0, Math.min(1, raw))` 限制在有效范围

### 10. server.ts handler 消息类型
**文件**: `src/lib/acp-protocol/server.ts`
**状态**: 上轮审查后已修复。当前所有 handler 使用正确的 JSON-RPC 2.0 响应格式，`source` 字段使用 `'server' as const` 确保类型安全。无需额外修改。

### 11. client.ts — 背压死代码清理
**文件**: `src/lib/acp-protocol/client.ts`
**问题**: `messageQueue` 数组和 `backpressureThreshold` 声明存在但从未有消息被推入队列，`flushQueue()` 方法永远不会实际发送消息。
**修复**: 删除 `messageQueue`、`backpressureThreshold`、`queuedMessages` 声明和 `flushQueue()` 方法，以及 `sendRequest()` 中对它们的引用。

### 12. kv-cache.ts — FNV-1a 哈希精度
**文件**: `src/lib/token/kv-cache.ts:51-63`
**问题**: 使用 `Math.imul()` 进行 FNV-1a 哈希计算，该函数将结果截断为 32 位整数，但注释声称是 "64-bit hash"，实际只有 32 位精度，哈希冲突率高于预期。
**修复**: 改用 `BigInt` 进行完整 64 位运算，使用 `0xcbf29ce484222325n` 和 `0x100000001b3n` 作为常量和 64 位掩码 `0xffffffffffffffffn`，输出 16 位十六进制字符串。

## P3 — 低优先级 (4项)

### 13. model-router.ts — 中文 token 估算
**文件**: `src/lib/token/model-router.ts:178`
**问题**: `prompt.length / 4` 假设每 4 个字符约 1 个 token，对英文合理但对中文/CJK 字符严重低估（中文每字约 1.5 token）。
**修复**: 新增 `estimateTokenCount()` 函数，使用正则匹配 CJK 字符范围（平假名、片假名、CJK 统一汉字、韩文、CJK 扩展），对 CJK 字符按 1.5 token/字计算，非 CJK 字符按 0.25 token/字符计算。

### 14. goal_graph.rs — 死代码 + 错误静默
**文件**: `src-tauri/src/goal_graph.rs` 和 `src-tauri/src/topology.rs`
**问题**:
- `topological_order()` 第 182-188 行有一个空循环体，是重构遗留的死代码
- `topology.rs` 中 `let _ = graph.add_goal(goal)` 静默丢弃了 `add_goal()` 可能返回的错误

**修复**:
- 删除 `topological_order()` 中的空循环死代码
- 将 `let _ = graph.add_goal(goal)` 改为 `if let Err(e) = ... { eprintln!(...) }`，记录错误但不中断执行

### 15. Tauri command 命名统一
**文件**: `src-tauri/src/swarm_orchestrator.rs:819`, `src-tauri/src/lib.rs:449`
**问题**: `swarm_orch_cancel_task` 不符合 `swarm_` 前缀的命名规范，与前端调用 `swarm_cancel_task` 不一致。
**修复**: 重命名为 `swarm_cancel_task`，同步更新 `lib.rs` 中的命令注册。前端 3 处调用已使用正确名称。

### 16. Pipeline 拓扑实现
**文件**: `src-tauri/src/topology.rs`
**问题**: `Pipeline` 枚举变体已声明但无执行函数。
**修复**: 新增 `execute_pipeline()` 函数，实现 "分阶段并行" 的拓扑模式：将 goals 按 stage 分组，每个 stage 内的 goal 并行执行，stage 之间顺序依赖。每个 stage 中的 goal 依赖前一个 stage 的所有 goal。
